# Design: Доставка наёмной техникой

## Context

Зачем это нужно, описано в proposal.md, требования лежат в `specs/`.

Как устроено сейчас:
- **Расчёт заказа.** Весь расчёт делает фронтенд: `frontend-v2/js/order-calc.js` (`run` и `toOrderPayload`). Сервер (`handlers/orders.js::sanitize`) только проверяет и сохраняет снимок.
- **Признак самовывоза.** Отдельной колонки нет, признак — строка `mixer_name = 'Самовывоз'`. По ней работают:
  - `orders.js::lockedFieldsChanged`;
  - `order-edit-diff.js::isSelfPickup`;
  - `order-edit.js` на фронте;
  - `sanitize` вычисляет из неё `selfPickup` для памяти клиента.
- **Статус в списке.** `mobile-orders.js::statusFor` и список на ПК ставят «Самовывоз» любому заказу с `tripCount = 0`.
- **Путевые листы.** Экран путевых показывает только заказы с `tripCount > 0`. Сервер (`waybill-entries.js`) отклоняет разнесение, если не осталось нераспределённых рейсов. Если у наёмного заказа 0 рейсов, он исключается сам, без новой логики.
- **Маска числа.** Её даёт общий `NumericInput.attach`: разряды, до двух знаков после запятой, `inputmode="decimal"`.
- **Подсказка «доставка в минус».** Есть только на телефоне (`mobile-calc.js`), строится по `deliveryBreakevenPerM3`. Сейчас это значение считается только при `trips > 0`.
- **Внешние системы.** Заказы ни с какой внешней таблицей не синхронизируются, делить владение колонками не нужно.

## Goals / Non-Goals

**Goals:**
- Режим доставки становится явной колонкой. Магическая строка «Самовывоз» перестаёт быть источником истины.
- Формулы режимов «Своя» и «Самовывоз» остаются прежними, байт в байт по результату.
- Старый закэшированный фронтенд продолжает оформлять заказы «Своя» и «Самовывоз».

**Non-Goals:**
- Перенос расчёта на сервер.
- Отказ от записи «Самовывоз» в `mixer_name`. Снимок остаётся для v1 и печатных форм.
- Изменения в v1 (`frontend/`).

## Decisions

### 1. Модель данных

```sql
ALTER TABLE orders ADD COLUMN IF NOT EXISTS delivery_mode TEXT NOT NULL DEFAULT 'own';
ALTER TABLE orders ADD COLUMN IF NOT EXISTS hire_rate_per_m3 NUMERIC;   -- NULL, если не найм
UPDATE orders SET delivery_mode = 'pickup' WHERE delivery_mode = 'own' AND mixer_name = 'Самовывоз';
-- CHECK (delivery_mode IN ('own','pickup','hired')) — DROP CONSTRAINT IF EXISTS + ADD, как waybill_entries_source_check
```

`UPDATE` идемпотентен: `schema.sql` накатывается на каждом старте, а новые заказы «Своя» никогда не получают `mixer_name = 'Самовывоз'`.

Почему так, а не иначе:
- Отдельный булев `is_hired` отвергнут: тогда пришлось бы держать два несовместимых признака, `is_hired` и `mixer_name = 'Самовывоз'`.
- Одна колонка режима закрывает все три состояния.

### 2. Снимок `mixer_name` у наёмного заказа — «Найм»

Наёмный заказ сохраняется так же, как самовывоз:
- `mixer_name = 'Найм'`;
- `mixer_id = NULL`;
- `mixer_plate = ''`;
- `trip_count = 0`;
- `max_load_m3 = NULL`;
- `neighbor_city = false`;
- все «на рейс» поля равны 0.

Так колонка «Миксер» в CSV, v1 и печати осмысленна без доработок. Источник истины при этом `delivery_mode`, а не `mixer_name`.

### 3. Сервер: режим, совместимость, проверки

`sanitize` читает `body.deliveryMode`. Если поля нет (старый фронтенд), режим выводится из `mixerName`: «Самовывоз» → `pickup`, иначе `own`. Для `hired` сервер требует:
- `hireRatePerM3 > 0`, иначе 400 «Укажите ставку найма»;
- `tripCount = 0`, иначе 400. Расчёт делает фронт, а сервер не даёт наёмному заказу попасть в путевые.

Для остальных режимов `hire_rate_per_m3` пишется как NULL, даже если ставка пришла в запросе. Признак `selfPickup` для памяти клиента выводится из режима: `deliveryMode === 'pickup'`.

`rowToOrder` отдаёт `deliveryMode` (текст) и `hireRatePerM3` (число или null).

### 4. Расчёт на фронте (`order-calc.js`)

`run` получает `deliveryMode` и `hireRate` вместо `selfPickup`. Для совместимости внутренних вызовов `selfPickup` равен `deliveryMode === 'pickup'`.

Ветка `hired`:
- `deliveryReady`: адрес заполнен и `hireRate > 0`;
- `trips = 0`, все «на рейс» поля равны 0;
- `deliveryCostTotal = hireRate × saleVolume`;
- выручка и прибыль доставки считаются по общей формуле.

`deliveryBreakevenPerM3` для найма равен `deliveryCostTotal / saleVolume`, то есть ставке. Условие `trips > 0` для найма снимается.

`toOrderPayload` добавляет в payload:
- `deliveryMode`;
- `hireRatePerM3`;
- `mixerName: 'Найм'`, `mixerId: null`;
- `distanceKm`: введённые км или 0.

### 5. Блокировки и журнал исправлений

`lockedFieldsChanged` сравнивает `row.delivery_mode` с `f.deliveryMode` вместо проверки строки «Самовывоз». Сравнение миксера и загрузки остаётся.

В `order-edit-diff.js`:
- поле `selfPickup` («Самовывоз: да/нет») заменяется полем `deliveryMode` с подписью «Доставка» и значениями Своя / Самовывоз / Найм;
- добавляется `hireRatePerM3` с подписью «Ставка найма» и единицей ₽/м³, NULL показывается как «—»;
- строка «Миксер» показывает «—» для любого режима, кроме `own`.

Старые записи журнала хранят готовый текст (`changes` в JSON), их не мигрируем.

На фронте `order-edit.js`:
- в `formState` появляются `deliveryMode` и `hireRate`;
- `lockedFields` содержит `deliveryMode` вместо `selfPickup`;
- в `SNAPSHOT_FIELDS` добавляются `deliveryMode` и `hireRatePerM3`;
- нормализация снимка для `pickup` и `hired` одинаковая, кроме адреса и км: у найма они остаются.

### 6. Память клиента (`clients.applyOrder`)

Три ветки по режиму:
- **`pickup`:** как раньше.
- **`hired`:** `UPDATE clients SET vat_gross, self_pickup = FALSE, site_address, site_distance_km, delivery_charge_per_m3, terms_*`. Колонки `mixer_id`, `max_load_m3`, `site_neighbor_city` не трогаем.
- **`own`:** как раньше.

Колонку режима в `clients` не добавляем: найм не запоминается.

### 7. Форма (ПК и телефон)

Тумблер `#m-self-pickup` / `#mc-self-pickup` заменяется сегментом `.seg` из трёх кнопок. Этот же компонент уже используется для переключателя НДС. Новое поле «Ставка найма, ₽/м³» с `NumericInput.attach` видно только в режиме `hired`. Активность полей определяется по режиму:

| Режим | Активны | Неактивны |
|---|---|---|
| `pickup` | — | всё |
| `hired` | адрес, км, цена клиенту, ставка | миксер, загрузка, соседний город, топливо, мочевина |
| `own` | всё | — |

Ставка при включении найма пустая. Обязательные поля подсвечиваются тем же механизмом, что и сейчас (`missingDelivery`). Подсказка «Укажите ставку найма» показывается у поля ставки.

Подстановка памяти (`termsToApply` + `applyTerms` в `screen-main.js` / `mobile-calc.js`):
- если `terms.selfPickup`, включается `pickup`;
- иначе, если текущий режим `hired`, он сохраняется, а адрес, км и цена доставки подставляются;
- в остальных случаях включается `own`.

Сброс формы ставит `own` и очищает ставку.

Для сводки на телефоне `ClientMemory.deliverySummary` получает режим и ставку и отдаёт «Доставка · Найм · 500 ₽/м³ · 30 км».

### 8. Список, карточка, CSV, Telegram

- **Статус.** `statusFor` (телефон) и статус на ПК: `deliveryMode === 'hired'` → «Найм» раньше проверки `!tripCount`.
- **Карточка** (`screen-orders.js`). Для найма блок «Доставка — расход» показывает одну строку «Найм: ставка × объём = расход» и «Итого расход».
- **CSV.** Две колонки в конце. Названия режимов берутся из общей таблицы `own → Своя`, `pickup → Самовывоз`, `hired → Найм`.
- **Telegram.** В `notifyOrderCreated` для найма строка «Доставка: Найм · <ставка> ₽/м³» вместо «Миксер: …».

## Risks / Trade-offs

- **[Старый фронтенд в кэше у работника]** Он присылает заказ без `deliveryMode`. → Режим выводится из `mixerName`, заказы «Своя» и «Самовывоз» оформляются как раньше. Найм в старой версии просто недоступен.
- **[Исправление старым фронтендом заказа «Найм»]** Старая форма не знает режима «Найм» и не найдёт миксер «Найм», поэтому оператору придётся выбрать миксер или самовывоз. Это осознанная смена режима, и брать режим из строки заказа было бы неверно. → Без `deliveryMode` режим выводится из `selfPickup`, а иначе из `mixerName`: «Самовывоз» → `pickup`, «Найм» → `hired` (тогда нужна ставка, иначе 400), остальное → `own`.
- **[Бронь у наёмных заказов не списывается]** Это осознанно, см. Out of Scope. Та же ситуация уже есть у самовывоза. → Отдельный change на списание без путевых.
- **[Строки «Самовывоз: да → нет» в старом журнале рядом с новыми «Доставка: …»]** → Это допустимо, журнал хранит текст на момент правки.

## Migration Plan

1. Выкатка штатная (`deploy_server_paths`): `schema.sql` добавит колонки и проставит `pickup` старым самовывозам при старте.
2. Проверить на проде: `SELECT delivery_mode, count(*) FROM orders GROUP BY 1`. Число `pickup` должно совпадать с числом заказов, где `mixer_name = 'Самовывоз'`.
3. Откат: вернуть предыдущий образ. Новые колонки аддитивны, старый код их не читает. Наёмные заказы в старом коде выглядят как заказы с миксером «Найм» и 0 рейсов, расчёт в них уже сохранён снимком.
