# Design

## Context

Мотивация описана в proposal.md (раздел «Why»), требования — в `specs/waybills/*`.

Как сейчас устроен код:
- Документы 4-С не хранятся. Их собирает `buildWaybill4sDocuments` в `backend/router.js` из **выбранных** записей `waybill_entries`, группируя по `driverId|mixerId|tripDate`.
- Одометр уже считается по полной истории техники (`ORDER BY mixer_id, trip_date, created_at, id`).
- Время (`dayElapsedMinutes`) и остаток топлива (`dayFuelBalance`) живут внутри группы водителя и сбрасываются на каждого водителя и каждый день.
- Норма листа восстанавливается как Σ(`tripCount × fuelCostPerTrip`) / `fuelPricePerLiter`. При цене 0 норма тоже 0.
- `applyFuelFactVariance` масштабирует факт под сумму нормы выгрузки на основе `Math.random()`. Каждая выгрузка даёт новые цифры.
- Номер листа выдаётся через `waybill_doc_numbers(doc_key, number)` по ключу `driver-mixer-date-pN`.
- `mixer_id` в `waybill_entries` хранит id миксера **или** инертовоза.

## Goals / Non-Goals

**Goals:**
- Один чистый (без БД) модуль расчёта листов техники. Его используют и выгрузка 4-С, и сводка, поэтому цифры совпадают по построению.
- Детерминизм: одни и те же рейсы и коэффициенты всегда дают одни и те же литры.
- Расчёт тестируется без БД: на вход рейсы, настройки и коэффициенты, на выход листы.

**Non-Goals:**
- Хранить документы 4-С как сущность. Они по-прежнему собираются на лету.
- Блокировать правку распечатанных листов.
- Менять расчёт `fuel_cost_per_trip` и всё, что от него зависит.
- Сводка на мобильном экране (`mobile-waybills.js`): только десктоп.

## Decisions

### 1. Отдельный модуль `backend/waybill-docs.js`

Логика переезжает из `router.js` в модуль из трёх частей:
- `orderVehicleEntries(entries)` — сортировка рейсов одной техники по `vehicle-timeline`: дата → блок водителя (по min `created_at` его записей за день) → `created_at` → `id`.
- `buildVehicleDocs(entries, cfg, baselineKm)` — разбиение на листы (≤ 3 ездки), время, одометр, норма, маршруты и legs. Чистая функция, литров топлива кроме нормы не считает.
- `applyFuelChain(docs, coeffByKey)` — проходит листы техники по порядку, считает факт, выдано и остатки. Чистая функция.
- Обёртка с БД `loadVehicleDocs(vehicleIds, untilDate)` грузит полную историю, базовый пробег и коэффициенты (с созданием недостающих) и возвращает листы со всеми цифрами.

Почему так, а не правка `buildWaybill4sDocuments` на месте: функция уже ~300 строк в роутере и смешивает SQL с расчётом. Сводке нужен тот же расчёт без печати. Альтернатива «сводка вызывает `buildWaybill4sDocuments`» привязала бы сводку к выбору записей и к печатным полям.

### 2. Время и одометр — единый курсор техники

`buildVehicleDocs` идёт по упорядоченным рейсам одной техники. Курсор времени сбрасывается в `shiftStartMinutes` только при смене даты, а при смене водителя продолжается. Одометр — сквозной от `odometer_baseline_km`. Отдельный проход истории ради одометра (`odometerStartByEntryId`) больше не нужен: одометр считается тем же проходом и в том же порядке.

Последствие: если раньше записи двух водителей одного дня создавались вперемешку, одометр листов этого дня изменится, потому что порядок теперь «блоками по водителю». Для дней с одним водителем ничего не меняется.

### 3. Ключ листа и номер части

Ключ остаётся прежним, `driverId-mixerId-tripDate-pN`, где N — номер части внутри блока водителя за день. Значит, `waybill_doc_numbers` продолжают работать без миграции. Коэффициенты привязываются к тому же ключу.

### 4. Хранение коэффициентов — новая таблица

```sql
CREATE TABLE IF NOT EXISTS waybill_doc_fuel (
  doc_key   TEXT PRIMARY KEY,
  target_p  NUMERIC NOT NULL,  --  0.05 …  0.15
  start_s   NUMERIC NOT NULL,  --  0.05 …  0.10, используется только у первого листа техники
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Значения генерируются в Node (`Math.random()`) пачкой на недостающие ключи: `INSERT … ON CONFLICT (doc_key) DO NOTHING`, затем `SELECT`. При гонке двух запросов побеждает первая вставка, и оба получают одинаковые значения. `start_s` пишется всегда, чтобы при вставке рейса раньше первого листа не пришлось догенерировать.

Альтернатива — детерминированный псевдослучай от хеша ключа: без таблицы, но коэффициенты нельзя поправить вручную, а при смене алгоритма хеша изменятся все листы. Хранение проще объяснить и проверить. Ещё одна альтернатива — колонки в `waybill_doc_numbers`: эта таблица заполняется только при печати, а сводка не должна выдавать номера (спека `fuel-summary`), поэтому таблицы разные.

### 5. Снимок ставки `waybill_entries.fuel_rate`

`ALTER TABLE waybill_entries ADD COLUMN IF NOT EXISTS fuel_rate NUMERIC`. `validateAndBuild` уже читает `fuelRate` из карточки миксера или инертовоза, его просто нужно записать.

Бэкфилл старых записей:
1. Там, где `fuel_price_per_liter > 0`: точное восстановление `fuel_cost_per_trip / (2 × distance_km × fuel_price_per_liter) × 100`, то есть ставка на момент распределения.
2. Иначе — текущая ставка из карточки миксера или инертовоза.
3. Если не нашлось ни того, ни другого, остаётся 0, и лист считается «без нормы».

Бэкфилл идемпотентен (`WHERE fuel_rate IS NULL`), потом `SET NOT NULL DEFAULT 0` не делаем: NULL означает «не заполнено», и код трактует его как 0.

### 6. Округления

Порядок в `applyFuelChain`:
- норма листа — `round1` (до 0,1 л);
- факт — равен норме (без случайного отклонения);
- стартовый остаток — `round1(норма × s)`;
- выдано — `max(0, Math.round(факт − выезд + round1(норма × p)))`;
- возвращение — `round1(выезд + выдано − факт)`.

Все остатки кратны 0,1, поэтому печать и сводка совпадают без накопления ошибки. Лист с нормой 0 пропускает остаток насквозь, и коэффициенты для него не нужны.

### 7. Выгрузка 4-С

Маршрут `POST /api/waybill-entries/waybills.xlsx`:
1. По выбранным id берёт технику и максимальную дату.
2. Вызывает `loadVehicleDocs(vehicleIds, maxDate)`.
3. Оставляет листы, в которые входит хотя бы один выбранный рейс.
4. Выдаёт номера и печатает.

`waybill-xlsx-4s.js` печатает готовые `fuelIssued`, `fuelBalanceAtDeparture`, `fuelBalanceAtReturn`, `fuelFactLiters` и `totalFuelLiters` и больше ничего не считает (сейчас там `× 1.1`).

### 8. Сводка

`GET /api/waybill-entries/fuel-summary?from=YYYY-MM-DD&to=YYYY-MM-DD&plantId=&vehicleId=`, роль `manager`.
1. Выбирается техника, у которой есть рейсы в `[from, to]`, с учётом фильтров. Завод проверяется по `waybill_entries.plant_id`.
2. `loadVehicleDocs(ids, to)` считает листы этой техники.
3. Листы с `tripDate` в периоде агрегируются в строки: нормы, факты и выдано суммируются, начало берётся у первого листа периода, конец — у последнего.
4. Флаг `mismatch` ставится, если `|начало + выдано − списано − конец| > 0,05`.

Ответ — JSON: строки (id, название и тип техники, норма, списано, выдано, начало, конец, `mismatch`, число листов) и итог.

На фронте (`screen-waybills.js`) — сворачиваемый блок «Списание ГСМ» под списком записей: фильтры, таблица, итог, кнопка «Скачать xlsx». xlsx собирается на клиенте через `frontend-v2/js/xlsx-writer.js`, как другие таблицы v2. Фильтр называется «Завод», но на бэкенде параметр `plantId` трактуется как «подразделение рейса». Когда появятся подразделения, меняется только источник списка.

## Risks / Trade-offs

- [Перепечатка листов за прошлые даты даст другие цифры, чем первая печать: другой факт, остатки, а для смен — одометр и время] → Это ожидаемое следствие перехода. В proposal оно помечено как BREAKING. После деплоя за текущий месяц листы перепечатываются.
- [Расчёт по полной истории техники на каждую выгрузку и сводку] → Записей порядка тысяч, а расчёт линейный. Если станет медленно, история ограничивается последним листом с «нулевым» якорем. Пока не делаем.
- [Вставка рейса задним числом меняет уже подписанные последующие листы] → Решение пользователя (решение 11 grill): цепочка важнее неизменности. Защиты распечатанных листов нет, это Out of Scope.
- [Бэкфилл ставки по текущей карточке для записей с ценой 0 может не совпасть с историей] → Это касается только записей с ценой топлива 0, которые раньше и так печатались без топлива.
- [`GET`-сводка пишет в БД (коэффициенты)] → Запись идемпотентна и невидима для пользователя. Альтернатива «не фиксировать в сводке» нарушила бы совпадение сводки и печати.

## Migration Plan

1. В `schema.sql` добавить колонку `fuel_rate`, бэкфилл и таблицу `waybill_doc_fuel`. Всё идемпотентно и накатывается при старте, как остальная схема.
2. Деплой стандартный, перед ним — бэкап БД.
3. Откат: вернуть код. Колонка и таблица остаются и старому коду не мешают.
