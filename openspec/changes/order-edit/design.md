# Design: Исправление оформленных заказов

## Context

Мотивация — в proposal.md, требования — в `specs/orders/order-edit/spec.md`.

Что есть сейчас:
- Расчёт заказа целиком на фронтенде: `frontend-v2/js/order-calc.js` (`run` + `toOrderPayload`). Сервер (`handlers/orders.js::sanitize`) только валидирует и сохраняет снимок. Для исправления так же.
- `crudRoutes('/api/orders', …)` регистрирует `PUT /api/orders/:id` с `role: null`, но у `orders` нет `update()`. Маршрут существует, а при вызове падает.
- Работник без сессии. Его завод определяется по `?token=` (`plants.resolveToken`, у общей ссылки `universal: true`). `Plant.currentToken()` на фронте уже умеет добавлять токен к запросу (`frontend/js/shared/state.js`).
- Бронь: `stock.reserve` при создании, `stock.release` снимает остаток брони, посчитанный по журналу движений. При разнесении путевых бронь частично списывается долей `рейсы записи / orders.trip_count`.
- Память клиента: `clients.applyOrder(executor, f)`, вызывается в транзакции создания.
- В сессии хранится только роль, логинов нет.
- Заказы не синхронизируются ни с какой внешней таблицей. Синхронизация с Mail.ru есть только у ДДС, и её этот change не трогает. Разделения колонок с внешней системой не требуется.

## Goals / Non-Goals

**Goals:**
- Один серверный путь сохранения исправления (`orders.update`) со всеми проверками в одной транзакции.
- Diff и текст журнала считает сервер, чтобы журнал нельзя было подделать с фронтенда.
- Формулы `order-calc.js` не меняются, форма переиспользуется.

**Non-Goals:**
- Перенос расчёта на сервер.
- Хранение цен справочников на дату заказа.
- Сжатие или ротация журнала.

## Decisions

### 1. Модель данных

```sql
ALTER TABLE orders ADD COLUMN IF NOT EXISTS inserted_at TIMESTAMPTZ;
UPDATE orders SET inserted_at = created_at WHERE inserted_at IS NULL;
ALTER TABLE orders ALTER COLUMN inserted_at SET DEFAULT now();
ALTER TABLE orders ALTER COLUMN inserted_at SET NOT NULL;
ALTER TABLE orders ADD COLUMN IF NOT EXISTS recipe_id TEXT;   -- без FK: снимок, рецепт может быть удалён
ALTER TABLE orders ADD COLUMN IF NOT EXISTS mixer_id TEXT;    -- без FK, то же
ALTER TABLE orders ADD COLUMN IF NOT EXISTS version INTEGER NOT NULL DEFAULT 1;

CREATE TABLE IF NOT EXISTS order_edits (
  id TEXT PRIMARY KEY,
  order_id TEXT NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  edited_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  actor_role TEXT NOT NULL,          -- 'worker' | 'manager' | 'admin'
  actor_plant_name TEXT NOT NULL DEFAULT '',  -- завод работника; для общей ссылки — завод заказа
  changes JSONB NOT NULL,            -- [{ field, label, before, after }] — уже отформатированные строки
  profit_before NUMERIC NOT NULL,
  profit_after NUMERIC NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_order_edits_order ON order_edits(order_id, edited_at DESC);
```

- `inserted_at` вместо отсчёта окна от `created_at`: `created_at` уже редактируется (`updateDate`). Тот же приём, что у `cash_entries.inserted_at`. Миграция в четыре шага идемпотентна: повторный прогон `db.migrate()` ничего не меняет.
- `recipe_id`/`mixer_id` без FK, по тому же принципу снимка, что `recipe_name`. Пишутся в `create` из уже приходящих `recipeId`/`mixerId` (сейчас они идут только в память клиента).
- `version` вместо сравнения `updated_at`: целое число без проблем с точностью времени при сериализации. Увеличивается при каждом `update` и `updateDate`.
- `changes` хранит готовые строки, а не сырые значения. Журнал показывает то, что было на момент правки, даже если потом переименуют рецепт или клиента. Альтернатива — сырые значения и форматирование при показе. Отвергнута: названия по id со временем меняются.

### 2. Маршрут и права

`PUT /api/orders/:id` объявляется явно, вместо записи из `crudRoutes`: PUT из `crudRoutes` для заказов отфильтровывается, как уже сделано у `/api/clients`. Вызов: `role: null`, обработчик получает `role` и `query.token`.

- Есть роль `manager`/`admin`: проверок окна и завода нет. `actor_role` = роль.
- Нет роли: обязателен `?token=` → `plants.resolveToken`. Нет токена или он неверный — 401/400. Дальше в `orders.update` передаётся `actor = { role: 'worker', plantId }`. У общей ссылки `plantId = null`, то есть любой завод.
- В `orders.update` (под `SELECT … FOR UPDATE`):
  1. заказ существует, иначе 404; не отменён, иначе 409 «Заказ отменён»;
  2. `version` из тела совпадает, иначе 409 «Заказ уже исправили — откройте заново»;
  3. работник: `inserted_at >= now() - interval '24 hours'`, иначе 403 «Исправить заказ можно в течение суток — обратитесь к менеджеру»; `actor.plantId` пуст или равен `orders.plant_id`, иначе 403; `body.plantId === orders.plant_id`, иначе 403;
  4. если есть `waybill_entries` по заказу: заблокированные поля (`recipe_id`/`recipe_name`, `sale_volume`, самовывоз, `mixer_id`/`mixer_name`, `max_load_m3`) не изменились, иначе 409 «По заказу есть путевые листы — сначала удалите их».

Альтернатива — отдельный маршрут `/api/orders/:id/edit`. Отвергнута: PUT по id уже объявлен и сейчас сломан, правильнее его починить.

### 3. Валидация тела

Тело — тот же payload, что `toOrderPayload`, плюс `version`. Проверяет та же `sanitize()`: клиент обязателен и существует, рецепт обязателен (`recipeName`). `createdAt` в теле — дата заказа, она редактируется. `inserted_at` из тела не читается никогда.

### 4. Бронь

- **Путевых нет:** `stock.release(client, id, 'Исправление заказа')`, затем `DELETE FROM order_materials`, вставка новых строк и `stock.reserve(...)`. Остаток брони считается по журналу, поэтому повторное исправление тоже корректно.
- **Путевые есть:** `order_materials` и бронь не трогаются вообще, пришедшие `materials` игнорируются. Иначе `release` снимет только несписанный остаток, а `reserve` поставит полную бронь, и уже списанная доля задвоится. Объём и рецепт в этом случае заблокированы, а бронь и так соответствует заказу. Себестоимость за м³ обновляется из тела, по текущим ценам.

### 5. Память клиента

После сохранения заказа в той же транзакции:

```sql
SELECT id FROM orders WHERE client_id = $1 AND cancelled_at IS NULL
ORDER BY created_at DESC, inserted_at DESC LIMIT 1
```

Если результат — исправляемый заказ, вызывается `clients.applyOrder(client, f)`. Проверка делается уже по новым `client_id` и `created_at`, поэтому смена клиента и даты учтены. Память прежнего клиента не трогаем. `applyOrder` уже сам пропускает «Разовых покупателей».

### 6. Diff и форматирование

Сервер сравнивает старую строку и новые значения по фиксированному списку полей формы. У каждого поля своя подпись и формат:

| Поле | Подпись | Формат |
|---|---|---|
| plant_name | Завод | текст |
| created_at | Дата | `ДД.ММ.ГГГГ ЧЧ:ММ` (Europe/Moscow) |
| recipe_name | Рецепт | текст |
| sale_volume | Объём | `10 м³` |
| ship_date | Дата отгрузки | `ДД.ММ.ГГГГ` |
| client_name | Клиент | текст |
| sale_price + vat_applied | Цена | в режиме НДС заказа: `12 200 ₽ с НДС` / `10 000 ₽` |
| vat_applied | НДС | `с НДС` / `без НДС` |
| самовывоз (mixer_name = 'Самовывоз') | Самовывоз | `да` / `нет` |
| address | Адрес | текст, пусто → `—` |
| distance_km | Км | `12 км` |
| neighbor_city | Соседний город | `да` / `нет` |
| delivery_charge_per_m3 | Цена доставки | `600 ₽/м³` |
| mixer_name | Миксер | название, без госномера |
| max_load_m3 | Макс. загрузка | `5 м³`, пусто → `по вместимости` |
| fuel_price_per_liter | Цена топлива | `75,15 ₽/л` |
| urea_price_per_liter | Цена мочевины | `₽/л` |

Числа сравниваются с допуском 0,005, чтобы не ловить шум float. Если список изменений пуст, запись журнала и уведомление не создаются, а `version` не растёт. Прибыль (`total_profit`) — отдельная строка «Прибыль: было → стало», в `changes` она не входит.

Форматирование вынесено в чистый модуль `backend/order-edit-diff.js`: `diffOrder(before, after) → changes[]`. Его используют и журнал, и Telegram, и он тестируется без БД.

### 7. Telegram

`telegram.notifyOrderEdited({ order, changes, profitBefore, profitAfter, actorLabel })` в тот же чат заказов, fire-and-forget после COMMIT, как `notifyOrderCreated`:

```
✏️ <b>Заказ исправлен · Северный · СтройИнвест</b>
Заказ от 20.10.2026
Объём: 10 → 12 м³
Цена: 10 000 → 10 700 ₽
Прибыль: 34 000 → 41 200 ₽
Исправил: Работник · Северный
```

Все значения проходят через `escapeHtml`.

### 8. `updateDate` (v1)

Работает как раньше, но в транзакции: читает старую строку, обновляет, через тот же `diffOrder` строит изменения (`Дата`, `Завод`), пишет журнал, увеличивает `version` и после COMMIT отправляет уведомление. Роль берётся из маршрута (manager+). Ответ маршрута тот же, v1 не меняется.

### 9. Список заказов

`orders.list` и `getByIds` дополнительно возвращают `insertedAt`, `version`, `recipeId`, `mixerId`, `hasWaybills` и `edits[]`, новые сверху. Правки и признак путевых выбираются одним запросом на весь список (`WHERE order_id = ANY($1)`), без отдельного запроса на каждый заказ. `canEdit` вычисляет фронтенд по роли, `insertedAt` и `cancelledAt`. Сервер всё равно проверяет сам (см. §2).

### 10. Фронтенд

- `screen-orders.js` и `mobile-orders.js`: кнопка «Исправить» вместо окна «изменить дату и завод»; пометка «испр.» и раскрывающийся журнал.
- `screen-main.js` и `mobile-calc.js`: режим исправления `editingOrder`.
  - Заполнение из заказа: рецепт по `recipeId`, иначе по `recipeName` среди рецептов завода; миксер так же; клиент по `clientId`; дата отгрузки = `shipDate || дата createdAt`; цены топлива и мочевины ставятся с флагом «изменено вручную», чтобы `recalc` не затёр их текущими.
  - При заполнении `applyClientMemory()` не вызывается. Подстановка срабатывает только на событие смены клиента пользователем.
  - Заблокированные поля (`hasWaybills`) получают `disabled` и подсказку.
  - «Было → стало» сравнивает `totalRevenue`/`mixCost + deliveryCostTotal`/`totalProfit` заказа с текущим `lastCalc`.
  - «Сохранить исправление» активна, когда payload по полям формы отличается от исходного.
  - Отправка: `PUT /orders/:id` с `version`, у работника с `?token=` (через тот же хелпер, что и у `GET`). На 409 — сообщение и выход из режима.
  - Поле завода в режиме исправления: менеджер и admin выбирают завод в самой форме, работник видит его без выбора.
- `order-calc.js`: `toOrderPayload` без изменений, кроме того, что `createdAt` в режиме исправления берётся из формы, а не `new Date()`.

### 11. Правило в `openspec/config.yaml`

«Исправление проведённых записей — только сторно» заменяется на «Исправление проведённых денежных записей (ДДС, оплаты реестра) — только сторно, не правкой. Заказ — не проводка: исправляется на месте с журналом правок».

## Risks / Trade-offs

- [Расчёт присылает фронтенд, сервер ему доверяет] → Так же, как при создании, модель доверия не меняется. Журнал и уведомление считает сервер, поэтому подмена цифр видна в чате.
- [Пересчёт по текущим ценам меняет прибыль старого заказа при любой правке] → Решено в интервью: в пределах суток цены почти не меняются, а менеджер видит «было → стало» до сохранения и в журнале.
- [Поиск рецепта или миксера по названию у старых заказов может найти не тот, если на заводе два одинаковых названия] → Берём первое совпадение. Оператор видит выбранный рецепт и может его поменять. С этого change id сохраняются, и проблема уходит.
- [Общая ссылка работника даёт исправление на любом заводе] → Так же она уже даёт создание заказов на любом заводе. Окно 24 часа и журнал с уведомлением сохраняются.
- [`order_edits` растёт] → Одна строка на правку, объём мизерный по сравнению с `stock_movements`.
- [Конфликты слияния с `reestr-oplat` в `schema.sql`, `router.js`, `telegram.js`] → Миграции только дописываются в конец, правки точечные. Перед слиянием прогнать `git diff --stat main...order-edit` и полный `npm test`.

## Migration Plan

1. Деплой обычный: бэкап (`scripts/backup.sh`), затем `git pull && docker compose up -d --build`. `db.migrate()` добавит колонки и таблицу и заполнит `inserted_at` из `created_at`.
2. Старые заказы: `recipe_id`/`mixer_id` пустые, используется поиск по названию. Окно работника считается от `created_at`, так что старые заказы для работника недоступны.
3. Откат: вернуть предыдущий образ. Новые колонки и таблица старому коду не мешают: `SELECT *` их игнорирует, а `INSERT` перечисляет колонки явно.
