# Design: Пакетное решение по заявкам

## Context

Зачем это нужно — в proposal.md, требования — в `specs/payment-registry/bulk-decision/spec.md`. Текущее состояние:

- **Одиночное решение** — `handlers/registry.js::decide(id, body, ctx)`:
  - проверки, блокировка строки `withLockedRequest` (`SELECT … FOR UPDATE`), `UPDATE … decided_at=now()`;
  - после этого `notify(messageDecision, …)` без `await`: одно сообщение в чат реестра через `telegram.notifyRegistry`, с темой, если она задана.
- **Статус** не хранится, его считает `registry-calc.js::computeState`: группы `pending` / `approved` / `partial` / `postponed` / закрытые.
- **Телефон** — `mobile-registry.js`: карточки по группам `rgm-sep`, кнопки решения `data-act` на карточке, делегированный клик по `#rgm-body`. Учредитель живёт только на этом экране (`app.js::bootOwner`).
- **ПК** — `screen-registry.js`: строки-кнопки `.rg-row` в группах `.rg-group`, клик открывает карточку.

## Goals / Non-Goals

**Goals:**
- Пакет использует ту же логику решения, что и одиночное «Одобрить без суммы» и «Отложить». Отдельной ветки бизнес-правил нет.
- Один запрос к серверу на пачку, одно уведомление на пачку.
- Логика выбора одна для телефона и ПК, различается только разметка.

**Non-Goals:**
- Транзакция «всё или ничего» на всю пачку. По решению интервью применяется частично.
- Оптимистичное обновление интерфейса до ответа сервера.

## Decisions

### 1. Сервер: `decideMany` поверх общего ядра решения

Из `decide` выносится внутренняя `applyDecision(client, cur, pays, decision, opts)`: проверки и `UPDATE`. Её вызывают и `decide`, и новая `decideMany`.

```
POST /api/registry/decisions   (registryRoles: admin, owner)
{ "ids": ["preq_…", …], "decision": "approved" | "postponed" }
→ 200 { "applied": [{ "id", "number", "recipient", "amount" }],
        "skipped": [{ "id", "number"|null, "reason" }] }
```

- **Проверка запроса.** `decision` — только `approved` или `postponed`, иначе 400. `ids` — массив от 1 до 100 строк, иначе 400 «За раз — не больше 100 заявок». Повторяющиеся id убираются.
- **Каждая заявка — своя короткая транзакция** через `withLockedRequest`, по очереди. Альтернатива — одна транзакция на всё. Отвергнута: сбой одной заявки откатывал бы остальные, а нужно частичное применение. К тому же длинная блокировка мешала бы параллельным действиям admin.
- **Допустимое состояние** — по `computeState` внутри блокировки:

  | Состояние | Одобрить | Отложить |
  |---|---|---|
  | `pending` | применяется | применяется |
  | `postponed` | применяется | остаётся как есть, считается применённым |
  | `approved` / `partial` / `paid` | пропуск «уже одобрена» / «уже оплачена» | пропуск «уже одобрена» |
  | `rejected` | пропуск «уже отклонена» | пропуск «уже отклонена» |
  | не найдена | пропуск «заявка не найдена» | то же |

- **Комментарий решения при пачке не меняется.** Одиночный `decide` по-прежнему берёт его из тела запроса.
- **Неожиданная ошибка** одной заявки пишется в лог и становится пропуском с причиной «ошибка сервера». Пачка продолжается.

### 2. Сводное уведомление

`messageBulk(decision, applied, origin)`:
- заголовок «Одобрено пачкой: K заявок на S ₽» или «Отложено пачкой: K заявок», слово «заявка» склоняется;
- до 15 строк `№ · получатель · сумма` и «…и ещё N»;
- ссылка на реестр учредителя без конкретной заявки.

Отправляется через `telegram.notifyRegistry` без `await`. При пустом `applied` ничего не отправляется. Одиночные `messageDecision` при пачке не вызываются.

### 3. Фронтенд: общий контроллер выбора

`Registry.createSelection(opts)` в `registry-common.js`:
- **состояние:** `Set` выбранных id и сами заявки — для суммы и подтверждения;
- **методы:** `enter`, `exit`, `toggle`, `toggleGroup`, `has`, `count`;
- **`sumKop`** — сумма в копейках;
- **`selectable`** — только `pending` и `postponed`;
- **`barHtml`** — HTML нижней панели;
- **`confirmAndApply(decision)`** — подтверждение, затем `POST /decisions`, затем итог.

Перерисовку экраны делают сами по колбэку `onChange`.

- **Подтверждение** — собственный модальный слой, а не `window.confirm`: нужен список заявок и крупные кнопки. На телефоне это лист снизу, на ПК — диалог по центру. Закрывается «Отменой», кликом по фону и Escape.
- **Итог:**
  - без пропусков — короткое уведомление «Одобрено 3 из 3»;
  - с пропусками — баннер «Одобрено 3 из 4. Не удалось: № — причина», висит до закрытия.

  После применения режим выключается, список перезагружается.
- **Телефон:**
  - в заголовке групп `pending` / `postponed` — «Выбрать», в режиме — «Выбрать все» / «Снять все»;
  - галочка слева у карточки, блок кнопок решения скрыт, тап по выбираемой карточке переключает отметку;
  - панель `position: sticky; bottom: 0` с `env(safe-area-inset-bottom)`.
- **ПК:**
  - колонка с `<input type="checkbox">` в начале строки, только в режиме;
  - «Выбрать» и «все» в заголовке группы, клик по строке в режиме переключает отметку;
  - та же панель внизу страницы.
- **Сброс режима** при смене фильтра или «Активные / Закрытые» — на обоих экранах.

## Risks / Trade-offs

- [Одобрить пачку по ошибке — это деньги] → обязательное подтверждение со списком и суммой. Явный вход в режим, кнопки одиночных решений в режиме скрыты.
- [Сто транзакций подряд на маленьком сервере] → каждая короткая, 100 заявок — это доли секунды. На время запроса «Применяем…», кнопки заблокированы.
- [Учредитель и admin одновременно решают одни и те же заявки] → блокировка строки и проверка состояния внутри неё. Такие заявки уходят в «пропущенные» с причиной.

## Migration Plan

Схема БД не меняется. Деплой обычный. Откат — предыдущий образ.
