# Design: Фильтрация и поиск в списке заказов

## Context

- `frontend-v2/js/screen-orders.js` строит экран «Заказы» на ПК из `State.data.orders`.
  - Отбор есть только по заводу: модульная переменная `plantFilterValue` и функция `filteredOrders()`.
  - От `filteredOrders()` уже питаются список с разбивкой по дням, плитки (`renderKpi`) и CSV (`exportToExcel`).
  - Если выбранного завода больше нет, выбор сбрасывается (`renderPlantFilter`).
- `GET /api/orders` (`backend/handlers/orders.js::list`) отдаёт менеджеру и admin всю историю, а работнику по ссылке — заказы его завода за 7 дней. Отбор по заводу для менеджера и admin уже работает в браузере.
- Заказ хранит ссылку на клиента `clientId` (в БД `ON DELETE SET NULL`) и снимок имени `clientName`. Справочник клиентов приходит в `State.data.clients`.
- Пометки строки:
  - «Найм» и «Самовывоз» — `OrderEdit.deliveryModeOf(order)` (change `order-hired-delivery`);
  - «Отменён» — `cancelledAt`;
  - «с НДС» — `vatApplied`;
  - «испр.» — `OrderEdit.editLines(order).length > 0`.
- Чистые функции фронта проектируются как UMD-модули (`window.X` + `module.exports`) и тестируются через `node:test` в `backend/test/*-ui.test.js`. Образец — `order-edit.js` и `order-edit-ui.test.js`.
- Подсказки при вводе уже сделаны в реестре оплат (`registry-common.js`, класс `.rg-suggest`): собственный выпадающий блок под полем.

## Goals / Non-Goals

**Goals:**
- Вся логика отбора — чистые функции без DOM, их можно покрыть тестами по сценариям спеки.
- Экран при открытии ведёт себя как сейчас: выбрано «Всё время», клиент и поиск пусты.

**Non-Goals:**
- Изменения сервера и API.
- Виртуализация или постраничная загрузка длинного списка.
- Общий компонент выпадающего списка с вводом для всех экранов: делаем локально для «Заказов».

## Decisions

### 1. Модуль `frontend-v2/js/order-filter.js`
UMD-модуль `OrderFilter` с функциями:
- `periodRange(period, from, to, now)` → `{ start, end }` (локальные `Date`, `end` — исключающая граница: начало следующего дня; `null` — нет границы). Меняет местами перепутанные даты.
- `inPeriod(order, range)` — по `order.createdAt`.
- `clientKey(order, clientsById, clientsByName)` → ключ группы клиента:
  - `id:<clientId>`, если ссылка есть;
  - `id:<id>`, если ссылки нет, а имя совпадает с нынешним именем клиента в справочнике;
  - `name:<clientName>`, если совпадения нет;
  - `none` для заказа без клиента.
- `clientOptions(orders, clients)` → `[{ key, label, count }]` по алфавиту (`localeCompare('ru')`). Подпись — нынешнее имя из справочника, иначе снимок имени.
- `matchesSearch(order, query)` — разбор на слова, нормализация (нижний регистр, `ё → е`), правило для чисел.
- `apply(orders, state, ctx)` → отобранный список. `state` = `{ plantId, period, from, to, clientKey, query }`, `ctx` = `{ clients, now }`.
- `csvFileName(range, now)` — имя файла выгрузки.
- `totals(orders)` → `{ count, volume, pay }`. Считает так же, как сейчас `renderKpi` (суммы по всем переданным заказам). Им пользуются и плитки, и заголовки дней, поэтому правила у них не разойдутся.
- `countLabel(n)` — «1 заказ», «3 заказа», «5 заказов», «11 заказов», «21 заказ».

Почему так, а не прямо в `screen-orders.js`: экран — IIFE с DOM, и проверить его можно только e2e. Отдельный модуль закрывает почти все сценарии спеки быстрыми `node:test`.

### 2. Поиск по «стогу» из полей
Для заказа собирается одна нормализованная строка: адрес, рецепт, завод, миксер и слова пометок («найм», «самовывоз», «отменен», «с ндс», «испр.»), разделённые `\n`. Обычное слово подходит, если оно — подстрока этой строки. Слово-число (`/^\d+([.,]\d+)?$/`) подходит, если `Math.abs(saleVolume − число) < 1e-9` или оно — подстрока строки. Перед подстрочным поиском запятая в числе остаётся как ввели.

Альтернатива — сопоставлять каждое слово с отдельными полями. Отклонена: результат тот же, а кода больше. Разделитель `\n` не даёт словам склеиться на стыке полей.

### 3. Состав списка клиентов
`clientOptions` считается от заказов после отбора по заводу и периоду, но до отбора по клиенту и поиску. Если ключ выбранного клиента не входит в список, он сбрасывается в «все» (так же устроен `renderPlantFilter`).

### 4. Поле «Клиент»
`<input class="inp">` с выпадающим блоком в стиле `.rg-suggest`:
- фокус открывает полный список (сверху «Все клиенты» и «Без клиента»);
- ввод сужает список по части подписи;
- клик или Enter выбирает пункт; Escape или уход фокуса возвращает подпись выбранного.

Совпадение с набранным текстом выделяется `<b>` (текст экранируется до вставки). Пока клиент выбран, в поле его подпись без числа заказов, справа крестик «очистить» (макет `OrdersFilterB`/`OrdersFilterD`). Набранный текст, который не стал выбором, ничего не отбирает.

Почему не `<datalist>`: в нём нельзя надёжно отличить выбор пункта от свободного ввода, нельзя показать «Без клиента» как пункт с особым смыслом, а вид в браузерах разный.

### 5. Состояние фильтров
Модульные переменные в `screen-orders.js` рядом с `plantFilterValue`. Они живут, пока страница не перезагружена, поэтому выбор переживает переход между экранами и `State.loadAll()` после отмены или исправления. `localStorage` не используется. Поле поиска перерисовывает только список и плитки, без пересоздания строки фильтров, чтобы не терялись фокус и курсор.

### 6. «Сбросить фильтры» сбрасывает и завод
Это допущение, которое не обсуждалось на интервью. Кнопка возвращает экран к виду при первом открытии, поэтому завод тоже становится «Все заводы». Иначе после сброса можно остаться с пустым списком из-за завода и не понять почему.

### 7. Имя CSV
- «Всё время»: прежнее выражение `'zakazy-' + new Date().toISOString().slice(0, 10)`, ничего не меняем.
- Другие периоды: `zakazy-<с>_<по>.csv` в местных датах `ГГГГ-ММ-ДД`.
- Нет нижней границы: `zakazy-po-<по>.csv`.

## Risks / Trade-offs

- [Длинная история у менеджера: поиск на каждую нажатую клавишу пересобирает список] → Перерисовка уже идёт по всему списку при смене завода. Если станет медленно, добавить задержку 150 мс перед отбором. Сервер не трогаем.
- [Сравнение объёма через float: 12,5 м³ хранится как 12.5] → Сравниваем с допуском 1e-9, ввод с запятой переводим в точку.
- [Два удалённых клиента с одинаковым именем окажутся в одном пункте] → Допустимо: пользователь различает клиентов по имени, а справочник имён не дублирует.
- [Работник видит «Всё время», но получает только 7 дней] → Это ожидаемо и записано в спеке. Подсказку не добавляем.

## Migration Plan

Только фронт. Деплой — обычное обновление статики. Откат — вернуть `screen-orders.js` и убрать `order-filter.js` из `index.html`. Миграций БД нет.
