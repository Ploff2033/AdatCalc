# Design

## Context

Что есть сейчас:
- **`clients`** хранит только `id`, `name`, `type`, `created_at`. Комментарий в `backend/schema.sql:404-409` прямо фиксирует, что клиент не привязан к заводу.
- **`GET /api/clients`** открыт всем без фильтра (`crudRoutes(..., { read: null, create: null, write: 'manager' })`). Работник по ссылке получает весь список.
- **Заказ** (`handlers/orders.js::create`) — снимок расчёта. Рецепт и миксер в нём хранятся по имени (`recipe_name`, `mixer_name`), их id в заказ не попадают. Самовывоз определяется по `mixerName = 'Самовывоз'` и пустому адресу. Завод заказа приходит в теле (`plantId`), токен при создании заказа не сверяется.
- **Рецепты** привязаны к заводу (`recipes.plant_id`), **миксеры** общие для всех заводов.
- **Форма заказа** есть в двух местах: `frontend-v2/js/mobile-calc.js` и `frontend-v2/js/screen-main.js`. Логика цены там общая: `priceDirty ? priceNetStored : recipe.salePrice`, цена хранится без НДС, `vatGrossMode` только отображает её с ×1,22.
- **Загрузка данных** (`frontend/js/shared/state.js::loadAll`): `/clients` грузится без фильтра завода, в отличие от рецептов и сотрудников (`withPlantFilter`).
- **Миграции**: `db.migrate()` при старте выполняет весь `schema.sql` одним запросом, то есть в одной неявной транзакции.

## Goals / Non-Goals

**Goals:**
- Хранить память клиента в БД и отдавать её вместе со списком клиентов, чтобы форма заполнялась без лишних запросов.
- Записывать память атомарно с заказом.
- Разделить список клиентов по заводам на сервере, а не только в интерфейсе.
- Сохранить совместимость: старый закэшированный фронтенд продолжает оформлять заказы.

**Non-Goals:**
- Перенос данных из истории заказов.
- Изменения формул, состава заказа, уведомлений, отчёта.
- Несколько объектов у клиента, история цен.
- Переход «завод → подразделение» (см. Risks).

## Decisions

### 1. Схема данных

Колонки в `clients` (все через `ADD COLUMN IF NOT EXISTS`, существующие строки получают значения по умолчанию):

| Колонка | Тип | Смысл |
|---|---|---|
| `plant_id` | `TEXT REFERENCES plants(id) ON DELETE RESTRICT`, NULL | завод; NULL = «Без завода». Никогда не `NOT NULL` в этом change |
| `vat_gross` | `BOOLEAN NOT NULL DEFAULT FALSE` | режим НДС клиента |
| `site_address` | `TEXT NOT NULL DEFAULT ''` | адрес объекта |
| `site_distance_km` | `NUMERIC` NULL | км в одну сторону; NULL = не задано |
| `site_neighbor_city` | `BOOLEAN NOT NULL DEFAULT FALSE` | соседний город |
| `delivery_charge_per_m3` | `NUMERIC` NULL | цена доставки для клиента; NULL = не задано |
| `self_pickup` | `BOOLEAN NOT NULL DEFAULT FALSE` | самовывоз |
| `mixer_id` | `TEXT REFERENCES mixers(id) ON DELETE SET NULL` | миксер; удаление миксера обнуляет поле |
| `max_load_m3` | `NUMERIC` NULL | ограничение загрузки миксера; NULL = по вместимости |
| `walk_in` | `BOOLEAN NOT NULL DEFAULT FALSE` | «Разовые покупатели (без памяти)» — общий клиент вроде «Физлицо» |
| `terms_updated_at` | `TIMESTAMPTZ` NULL | когда последний раз менялись условия |
| `terms_source` | `TEXT` NULL | `'order'` / `'crm'` |

Новая таблица `client_prices`:

| Колонка | Тип |
|---|---|
| `client_id` | `TEXT NOT NULL REFERENCES clients(id) ON DELETE CASCADE` |
| `recipe_id` | `TEXT NOT NULL REFERENCES recipes(id) ON DELETE CASCADE` |
| `price_net` | `NUMERIC NOT NULL` (≥ 0) |
| `updated_at` | `TIMESTAMPTZ NOT NULL` |
| `source` | `TEXT NOT NULL` — `'order'` / `'crm'` |
| `source_label` | `TEXT NOT NULL DEFAULT ''` — для показа: «Заказ · Завод 1» / «CRM · manager» |

`PRIMARY KEY (client_id, recipe_id)`.

В `orders` добавляется `max_load_m3 NUMERIC` NULL — фактическая загрузка, по которой посчитаны рейсы, **только если она меньше вместимости миксера**. Для заказов без ограничения, для самовывоза и для всех старых заказов значение NULL. Поэтому серверу не нужно знать вместимость, чтобы решить, писать ли строку в Telegram: достаточно `max_load_m3 IS NOT NULL`. Колонка добавляется в `ORDER_COLUMNS`; при чтении NULL отдаётся как `null`, а не как 0.

Почему так:
- **Отдельная таблица цен**, а не JSON в `clients`: каскадное удаление по рецепту и по клиенту делает БД, а запись идёт простым UPSERT.
- **NULL вместо 0** для км и цены доставки: «не задано» не путается с «0 км» и не затирает поле формы.
- **Комментарий** `schema.sql:404-409` обновляется: старое решение помечается как заменённое этим change.

`ON DELETE RESTRICT` по заводу дал бы пользователю сырую ошибку FK. Поэтому `handlers/plants.js::remove` добавляет `clients` в свою проверку «блокирующих» записей (`materials`, `recipes`, `employees`) и отвечает понятным 409.

### 2. Память пишется на сервере в транзакции заказа

`orders.create` после `INSERT INTO orders`, в той же транзакции:
1. **Назначение завода:** `UPDATE clients SET plant_id = $plant WHERE id = $client AND plant_id IS NULL`.
2. **Цена:** если в теле есть `recipeId` и рецепт принадлежит `plantId` заказа, выполняется `INSERT INTO client_prices ... ON CONFLICT (client_id, recipe_id) DO UPDATE` с `salePrice` заказа (он уже без НДС), `source = 'order'`, `source_label = 'Заказ · <plantName>'`.
3. **Условия:** `UPDATE clients SET vat_gross, self_pickup, terms_updated_at, terms_source = 'order'`. Если не самовывоз, дополнительно пишутся `site_address`, `site_distance_km`, `site_neighbor_city`, `delivery_charge_per_m3`, `mixer_id` и `max_load_m3`. `max_load_m3` берётся из `orders.max_load_m3` этого заказа: если ограничения нет, там NULL, и ограничение у клиента снимается. Значение `mixer_id` берётся, только если такой миксер существует, иначе пишется NULL.

Новые поля тела: `recipeId`, `mixerId`, `selfPickup`, `maxLoadM3`. `maxLoadM3` сохраняется в `orders.max_load_m3`, остальные поля в таблицу `orders` не попадают. В таблицу `orders` они не попадают, состав заказа не меняется. Если они не пришли (старый фронтенд из кэша), заказ создаётся как раньше, а цена и миксер в память не пишутся. Самовывоз в этом случае определяется по прежнему признаку `mixerName === 'Самовывоз'`.

Почему на сервере, а не отдельным запросом с фронта:
- «память меняется только при успешном заказе» выполняется автоматически, без окна, когда заказ создан, а память нет;
- работник не получает отдельного права писать память (требование «только через заказ»).

Конкурентность: оба UPDATE и UPSERT берут блокировку строки. Одновременные заказы выполняются по очереди, побеждает последний COMMIT. Ошибок и блокировок дольше одной транзакции нет.

### 2б. Разовые покупатели

Найдено при проверке миграции на копии прод-бэкапа (14.10.2026): «Физлицо» — общий клиент для случайных покупателей, под ним 21 заказ на Джаге и 16 на Теберде. Без отдельного режима первый заказ привязал бы его к одному заводу, а память подставляла бы следующему физлицу чужой объект.

`clients.walk_in = TRUE`:
- `applyOrder` выходит сразу: ни завода, ни цены, ни условий;
- `setPrice` отвечает 400;
- `update` с `walkIn: true` одним запросом стирает завод и условия, удаляет цены (CRM спрашивает подтверждение, если было что стирать);
- в форме `ClientMemory.priceFor/termsToApply` для такого клиента возвращают пусто — работает как без клиента;
- на экране «Клиенты» — отдельная группа «Разовые покупатели» (не «Без завода»), в карточке скрыты завод, «Объект и доставка» и «Цены».

После деплоя пользователь один раз отмечает «Физлицо» как разовых покупателей.

### 2а. Рейсы с учётом загрузки

`Calc.tripsForVolume(mixer, volume, maxLoad)` (`frontend/js/shared/calc.js`) получает третий необязательный параметр:
- `load = maxLoad > 0 ? min(maxLoad, capacity) : capacity`;
- `trips = max(1, ceil(volume / load))`.

Без третьего параметра поведение прежнее, другие вызовы не меняются.

`OrderCalc.run` принимает `maxLoad` и возвращает `effectiveLoad` и `loadLimited` (`effectiveLoad < capacity`). `toOrderPayload` кладёт `maxLoadM3 = loadLimited ? effectiveLoad : null`. Остальные формулы доставки не меняются: расход на рейс × рейсы.

Всё, что ниже по цепочке, уже берёт `orders.trip_count`, и эти места не трогаем:
- путевые листы (`waybill-calc.js:20`);
- ГСМ в путевых (`waybill-calc.js:84`, `waybill-xlsx.js:93`);
- списание материалов (`handlers/waybill-entries.js:9-14`).

`telegram.notifyOrderCreated`: если `order.maxLoadM3` не NULL, после строки «Объём» добавляется `'Рейсов: ' + tripCount + ' × ' + maxLoadM3 + ' м³ (ограничение подъезда)'`.

### 3. Список клиентов: фильтр завода на сервере

`/api/clients` GET переходит на `scopeByToken: true`, как у рецептов:
- **Работник по ссылке завода:** `plantId` берётся из токена, параметр запроса игнорируется.
- **Работник с универсальной ссылкой:** `plantId` из запроса (выбор в переключателе).
- **Manager и admin с `?plantId=`:** фильтр по заводу; без параметра — все клиенты (нужно экрану «Клиенты»).

Фильтр: `WHERE plant_id = $1 OR plant_id IS NULL`. Ответ: клиент + условия + `prices: [{ recipeId, priceNet, updatedAt, source, sourceLabel }]`. Цены собираются одним вторым запросом по списку `client_id`, без N+1.

`state.js` грузит `/clients` через `withPlantFilter`. Экран «Клиенты» грузит полный список отдельным запросом без `plantId`, по тому же приёму, что и «Персонал» (`screen-personnel.js` и его собственный `GET /api/employees` без фильтра).

### 4. Создание клиента получает завод

POST `/api/clients` становится отдельным маршрутом вместо `crudRoutes`, потому что нужен токен:
- **Работник по ссылке завода:** `plant_id` = завод из токена, `plantId` из тела игнорируется.
- **Работник с универсальной ссылкой:** `plantId` из тела. Токен проверяется, завод должен существовать.
- **Manager и admin:** `plantId` из тела, может быть пустым («Без завода»).

Форма передаёт `plantId` текущего завода. Назначение завода первым заказом (решение 2) подстраховывает случай, когда клиент создан без завода.

### 5. Правка памяти в CRM (manager+)

- `PUT /api/clients/:id`: расширяется полями `plantId`, `vatGross`, `siteAddress`, `siteDistanceKm`, `siteNeighborCity`, `deliveryChargePerM3`, `selfPickup`, `mixerId`. Ставит `terms_source = 'crm'` и `terms_updated_at = now()`.
- `PUT /api/clients/:id/prices/:recipeId` `{ priceNet }`: UPSERT с `source = 'crm'` и `source_label = 'CRM · <роль>'`. Рецепт должен принадлежать заводу клиента, иначе 400 «Рецепт другого завода». Клиенту «Без завода» цену добавить нельзя, сначала назначается завод.
- `DELETE /api/clients/:id/prices/:recipeId`: удаление строки цены.

Работник получает 401/403 от проверки роли в роутере, как на других `write: 'manager'`.

Смена завода клиента не удаляет цены. Они остаются в таблице и в карточке (с пометкой рецепта чужого завода), но форма нового завода их не находит, потому что рецепты там другие. Это осознанно: случайная смена завода не уничтожает введённые по КП цены.

### 6. Форма: «базовая цена» вместо прайса

В обеих формах вводится понятие базовой цены: `basePriceNet = ценаКлиента(recipeId) ?? recipe.salePrice`. Существующая логика `priceDirty ? priceNetStored : salePrice` меняется на `priceDirty ? priceNetStored : basePriceNet`. Отсюда сразу следует поведение из спеки:
- **выбор клиента** сбрасывает `priceDirty`, и цена становится ценой клиента;
- **смена рецепта** уже сбрасывает `priceDirty`, и цена становится ценой клиента по новому рецепту или прайсом;
- **«Вернуть прайс»** уже сбрасывает `priceDirty` и возвращает базовую цену.

При выборе клиента дополнительно подставляются `vatGrossMode`, самовывоз, адрес, км, соседний город, цена доставки, миксер (если `mixerId` есть в `State.data.mixers`) и макс. загрузка.

**Поле «Макс. загрузка».**
- Форма хранит только ограничение, а показывает `ограничение ?? вместимость миксера`. Без ограничения смена миксера сразу меняет показанное число, с ограничением — нет.
- Значение, равное вместимости, или пустое поле снимает ограничение.
- Раскладка: строка «Миксер | В одну сторону» становится «Миксер | Км | Загрузка» (на телефоне 1.3fr / 1fr / 1fr).
- Ограниченная загрузка: рамка поля оранжевая (`#B8481A`, как у изменённой цены), подсказка «рейсов: 4 вместо 3».
- Загрузка больше вместимости: подсказка-предупреждение «больше вместимости миксера (8 м³), считаем по 8».
- Сводка доставки при ограничении: «Доставка · 4 × 5 м³ · 30 км».

Подсказка под ценой на телефоне — с датой без года («от 01.10»), на ПК — полная. Других отметок о подстановке из памяти нет. Пустые значения (NULL, '') не перезаписывают поле формы. Подстановка делается один раз в обработчике `change` селекта клиента, а не в `render()`, иначе каждая перерисовка затирала бы ручную правку.

Общие чистые функции выносятся в новый `frontend-v2/js/client-memory.js`, подключаемый в `index.html`, чтобы не дублировать их в двух формах:
- `clientsForPlant`;
- `priceFor(client, recipeId)`;
- `priceHint(...)`;
- `termsToApply(client, mixers)`.

DOM каждая форма заполняет сама, как сейчас.

`resolveClientForSubmit` в обеих формах передаёт `plantId` при создании клиента. Тело заказа дополняется `recipeId`, `mixerId` и `selfPickup` через `OrderCalc.toOrderPayload`. Формулы в `order-calc.js` не меняются.

### 7. Экран «Клиенты»

Раскладка — по макетам `Clients*.dc.html` на canvas «AdatBeton Calc — редизайн» (https://claude.ai/artifact/9Hm2kphRF3SH727ut3grB1). Где макет противоречит спеке, верна спека:
- колонка «С НДС» заполнена у всех клиентов (в макете у клиента без НДС стоит «—»);
- период остаётся текущими сегментами (в макете — выпадающий список).

Из макета дополнительно берутся:
- объект под названием клиента в строке списка;
- итоги в заголовке группы;
- кнопка «Выбрать завод» в строке клиента без завода, открывает карточку;
- «Любой» в поле миксера, если миксер не задан;
- подпись миксера с вместимостью («Howo 752 · 8 м³»);
- пометка «рецепт <завода>» у цены по рецепту чужого завода;
- добавление цены строкой прямо в таблице цен;
- футер нового клиента «Отмена / Сохранить».

По образцу `screen-personnel.js`:
- **Сегменты:** «Все · N» и «<Завод> · N» вместо `cl-plant-filter`.
- **Группы:** по заводам плюс «Без завода».
- **Карточка (drawer):**
  - сегмент завода, тип, режим НДС;
  - блок «Объект и доставка»: адрес, км, цена доставки, миксер, макс. загрузка (плейсхолдер «по вместимости миксера»), соседний город, самовывоз;
  - блок «Цены»: строки «рецепт · без НДС / с НДС · дата · источник» с правкой и удалением, кнопка «Добавить цену» с выбором из рецептов завода клиента без цены.

Отчёт за период (заказов, объём, сумма) считается как раньше. Сегмент завода фильтрует и клиентов, и заказы в отчёте.

### Данные с внешними системами

Внешних таблиц и систем нет. Владелец всех новых колонок — это приложение: заказ пишет условия и цену, CRM пишет всё.

## Risks / Trade-offs

- **[Старый фронтенд из кэша не шлёт `recipeId` / `mixerId`]** → Заказ создаётся, цена и миксер в память не пишутся, остальные условия пишутся. После обновления страницы всё работает. Ошибкой не считаем.
- **[Заказ через API с `plantId` чужого завода клиента]** → Заказ создаётся (как и сейчас: токен на POST заказа не сверяется), цена пишется по рецепту этого завода, завод клиента не меняется. Ужесточать проверку завода заказа — вне рамок change.
- **[Оператор опечатался в цене и оформил заказ]** → Память получает ошибочную цену. Это осознанное правило «оператор — первая инстанция». Исправляется следующим заказом или в CRM, источник и дата видны в карточке.
- **[Клиенты «Без завода» видны на обоих заводах]** → До первого заказа или ручного назначения. Клиентов меньше 10, пользователь назначит их сам.
- **[Переход «завод → подразделение»]** (`openspec/config.yaml`) → Клиент привязан к `plants`, так же как заказы, рецепты и сотрудники. При переходе `clients.plant_id` переезжает вместе с `orders.plant_id`. Отдельной сущности здесь не закладываем.
- **[Оператор не заметил ограничение загрузки у клиента]** → Поле подставляется само и выделено оранжевым, сводка показывает «4 × 5 м³». Если нужна разовая полная загрузка, оператор возвращает вместимость, и ограничение у клиента снимается. Для следующего заказа его придётся поставить заново.
- **[Будущая интеграция с софтом завода меняет модель миксеров]** → `clients.mixer_id` с `ON DELETE SET NULL` не мешает удалению миксеров. Перенос или пересмотр — задача того change.

## Migration Plan

1. Бэкап: `docker compose exec db pg_dump -U calc calc > /root/AdatCalc/backups/backup_$(date +%Y%m%d_%H%M).sql`.
2. Деплой: `git pull origin main && docker compose up -d --build`. `db.migrate()` добавит колонки и таблицу. Существующие строки не меняются, ошибка откатывает весь `schema.sql`.
3. Проверка: экран «Клиенты» → все старые клиенты в группе «Без завода». **Первым делом** отметить «Физлицо» как «Разовые покупатели (без памяти)» — до первого заказа на него, иначе заказ привяжет его к своему заводу. Затем назначить заводы остальным, внести цены и объекты по КП.
