# Design: Автозаполнение заявки из счёта

## Context

Зачем это нужно — в proposal.md («Why»); требования — в `specs/payment-registry/autofill/spec.md`. Текущее состояние кода (change `reestr-oplat`):

- **Создание заявки.** Сначала `POST /api/registry/requests` с полями, затем каждый файл отдельным `POST /requests/:id/files` с сырым телом (`backend/registry-files.js`, проверка сигнатуры, до 10 МБ). Так устроена форма «Новая заявка» в `frontend-v2/js/screen-registry.js`: очередь файлов, загрузка после создания, «Повторить».
- **Фронтенд** без сборки: классические `<script>` в `frontend-v2/index.html`, общие модули в `window.*`. Excel и ZIP собраны руками (`xlsx-writer.js`, `zip-writer.js`), npm-зависимостей у фронтенда нет.
- **Сервер** — VPS с 1 ГБ RAM, на нём Node, Postgres и xray. Распознавание на сервер не ставим (решение интервью).
- **Образцы счетов** (3 шт., файлы вне репозитория):
  - ЛИКАРД — PDF с текстом и QR;
  - ИП — скан в PDF, только картинка, есть QR;
  - ФОРА — картинка без QR, со строкой «Оплатить не позднее».
- **Тестов фронтенда нет.** `npm test` гоняет только `backend/test/**/*.test.js`.

## Goals / Non-Goals

**Goals:**
- Весь разбор счёта идёт в браузере. Сервер получает уже готовую заявку тем же API, что и при ручном вводе, плюс два новых поля.
- Логика «текст/QR → поля» — чистая функция в одном файле, который грузится и в браузер, и в `node:test`.
- Тяжёлые библиотеки грузятся лениво, при первом броске файла. На скорость открытия реестра и других экранов они не влияют.

**Non-Goals:**
- Не выносим распознавание в Web Worker вручную: tesseract.js и pdf.js сами работают в своих воркерах.
- Не делаем обучение или настройку распознавателя под конкретных поставщиков.
- Не трогаем мобильные экраны.

## Decisions

### 1. Библиотеки — локально в `frontend-v2/vendor/`, ленивая загрузка

| Библиотека | Зачем | Сборка |
|---|---|---|
| pdf.js 3.11 (`pdfjs-dist`, legacy UMD) | текстовый слой и рендер страниц PDF в canvas | `pdf.min.js` + `pdf.worker.min.js` |
| jsQR 1.4 | поиск и декодирование QR на canvas | `jsQR.js` (UMD) |
| tesseract.js 7 (актуальная на 23.10.2026) | OCR | `tesseract.min.js`, `worker.min.js`, `tesseract-core*.wasm.js`, языки `rus` + `eng` |

- **pdf.js.** Берём ветку 3.x: начиная с 4.x pdf.js выходит только как ES-модуль, а проект живёт на классических `<script>` без сборки.
- **Языковые данные tesseract.** В пакетах `@tesseract.js-data/*` есть два варианта: стандартный `4.0.0` (rus 8,6 МБ) и компактный LSTM `4.0.0_best_int` (rus 2,7 МБ). Варианта `tessdata_fast` там нет. Замер в задаче 2.3 (Chromium, ядро LSTM, страница увеличена до ~2400 px):

  | Модель | Счёт | Время OCR | Уверенность | Поля |
  |---|---|---|---|---|
  | `4.0.0_best_int` | фото ФОРА (~900 px, без QR) | 3,6 с | 86 | все 7 совпали с эталоном |
  | `4.0.0` | фото ФОРА | 3,4 с | 86 | то же |
  | `4.0.0_best_int` | скан ИП в PDF (без текстового слоя) | 1,4 с | 64 | все совпали |
  | `4.0.0` | скан ИП в PDF | 1,4 с | 63 | то же |

  Разницы в результате нет, поэтому выбран **`4.0.0_best_int`**: он втрое легче. Ядро — только LSTM-сборки `*-lstm.wasm.js`. Небольшие фото перед OCR увеличиваются до ~2400 px по длинной стороне: на исходных ~900 px строка товара ФОРЫ распознавалась в мусор.
- **Без CDN.** Из России сторонние CDN бывают недоступны, к тому же файлы счетов не должны зависеть от чужого сервера. Отдаются тем же `static.js` с `Cache-Control: no-cache` и 304 по Last-Modified, так что после первой загрузки браузер берёт их из кэша.
- **Загрузчик** `RegistryAutofill.ensureLibs()` вставляет `<script>` по требованию, только при первом броске файлов. Сразу после этого запускается прогрев tesseract-воркера.
- **Альтернатива** — подключать всё сразу в `index.html`. Отвергнута: это лишние 5–25 МБ на каждый заход в программу, включая работников на заводах.

### 2. Конвейер распознавания одного файла

```
файл ─┬─ PDF ─→ pdf.js: страницы 1–2
      │         ├─ текстовый слой (getTextContent) → text
      │         └─ рендер в canvas (scale 2 ≈ 200 dpi) → canvases
      └─ фото ─→ <img> → canvas (длинная сторона ≤ 2400px)

canvases ─→ jsQR (весь лист; если не нашёл — 4 четверти листа) → qrPayload
text пустой или < 80 значимых символов ─→ tesseract(canvases, 'rus+eng') → ocrText

InvoiceParse.merge({ qr: parseQr(qrPayload), pdf: parseText(text), ocr: parseText(ocrText) })
  → { fields, sources, flags }
```

- **QR ищем всегда**, даже у PDF с текстом. Это дёшево (рендер уже есть), а QR — самый точный источник суммы и ИНН.
- **OCR запускается**, только если текстового слоя нет или он пустой: у сканов, упакованных в PDF, слой бывает из пары служебных символов. Порог в 80 значимых символов (буквы и цифры) отделяет такой «пустой» слой от настоящего текста.
- **Один tesseract-воркер на всю пачку**, файлы идут строго по очереди. Так проще и с памятью браузера, и с порядком появления на экране проверки.
- **Отрендеренные canvases** переиспользуются экраном проверки как просмотр счёта, PDF не рендерится второй раз.

### 3. `invoice-parse.js` — разбор без DOM, общий для браузера и Node

Файл `frontend-v2/js/invoice-parse.js` в стиле UMD: в браузере это `window.InvoiceParse`, в Node — `module.exports`. Тесты подключают его через `require('../../frontend-v2/js/invoice-parse')`.

- **`parseQr(payload)`**:
  - разбирает `ST0001x|Key=Value|…`;
  - кодировку по версии (`1` → cp1251, `2` → UTF-8, `3` → KOI8-R) выбирает браузерная часть: jsQR отдаёт байты (`binaryData`), их декодирует `TextDecoder`;
  - возвращает `{ name, inn: PayeeINN, sumKop: Number(Sum), purpose: Purpose }`. Ключи сравниваются без учёта регистра: у разных банков `Sum` и `SUM`.
- **`parseText(text)`** предварительно нормализует текст: `ё→е`, неразрывные пробелы, «№» с пробелами и без, латинские буквы-двойники в цифрах из OCR (`O→0` только внутри чисел). Дальше правила:
  - **№ и дата счёта**: `/сч[её]т(?:\s+на\s+оплату)?\s*№\s*([A-Za-zА-Яа-я0-9\-\/]+)\s+от\s+(дата)/i`. Дата — `ДД.ММ.ГГГГ` или «22 октября 2026», месяцы родительного падежа идут через словарь.
  - **Договор**: `/(договор[^\n№]*?)№\s*([^\s,]+)\s+от\s+(дата)/i` в строке «Основание:» или «Договор:». Тип договора (например «поставки нефтепродуктов») сохраняется, как в образце ФОРЫ.
  - **Сумма**: последнее число после «Итого к оплате / Всего к оплате / Итого:», в рублях с копейками, разделители `пробел`, `.` или `,`. Если подходящих строк несколько, берётся «к оплате», иначе максимальное «Итого».
  - **Получатель и ИНН**: блок рядом с «Поставщик», «Исполнитель», «Получатель» — название организации или ИП и ближайший `ИНН\s*(\d{10}|\d{12})`, при этом ИНН покупателя (см. ниже) исключается.
  - **Покупатель**: блок «Покупатель / Плательщик / Заказчик / Организация:» и его ИНН.
  - **Наименования**: строки таблицы между шапкой («Наименование», «Товары (работы, услуги)») и «Итого», без номера строки и чисел в хвосте. Количество с единицей добавляется, если оно есть («…, 1 150 л»).
  - **Срок**: `/(оплатить\s+не\s+позднее|сч[её]т\s+действителен\s+до)\s*(дата)/i`.
- **`merge(parts)`**:
  - приоритет полей — QR > текст PDF > OCR;
  - `flags[field]` выставляется в `missing` (не найдено), `ocr_only` (только распознавание картинки) или `conflict` (источники расходятся, и в `alt` лежат оба значения);
  - суммы сравниваются в копейках.
- **ИНН своей компании** (`OUR_INNS = ['2628063503']`) — константа в этом же файле. Список юрлиц не меняется годами, настраивать его через интерфейс незачем, а второе юрлицо добавляется одной строкой.

### 4. Сервер: две колонки и один запрос подсказок

```sql
ALTER TABLE pay_requests ADD COLUMN IF NOT EXISTS recipient_inn TEXT;
ALTER TABLE pay_requests ADD COLUMN IF NOT EXISTS invoice_number TEXT;
CREATE INDEX IF NOT EXISTS idx_pay_requests_inn ON pay_requests(recipient_inn) WHERE recipient_inn IS NOT NULL;
```

- **`create`/`update`** в `handlers/registry.js` принимают `recipientInn` (пусто или `^\d{10}(\d{2})?$`, иначе 400). `invoice_number` клиент не передаёт: сервер извлекает его из `basis` по шаблону «Счёт № …» (`invoiceFromBasis`) при каждом создании и правке. Так у номера один источник — «Основание», и дубли ловятся и у заявок, заведённых вручную. Решение пользователя: отдельное поле «№ счёта» лишнее, номер уже есть в основании. Ответ и список отдают `recipientInn` и `invoiceNumber`.
- **`GET /api/registry/lookup?inn=…&invoiceNumber=…`** (admin) отвечает одним вызовом на файл:
  ```json
  { "defaults": { "unitId": "…", "categoryId": "…", "applicant": "Руслан", "fromNumber": "201026-9" } | null,
    "duplicates": [ { "id": "…", "number": "221026-14" } ] }
  ```
  - `defaults` берутся из последней по `created_at` заявки с этим ИНН. Скрытый unit или category возвращается как `null`, заявитель — как есть.
  - `duplicates` — заявки с тем же ИНН и тем же `invoice_number`. Номер сравнивается после нормализации на сервере: без пробелов и регистра.
- **Альтернатива** — два отдельных эндпоинта. Отвергнута: это два запроса на каждый файл пачки ради одного и того же поиска по ИНН.
- **Карточка заявки** (десктоп) и ручная форма получают одно необязательное поле — «ИНН получателя», рядом с «Получатель». Поля «№ счёта» нет (см. выше).

### 5. Экран проверки — `registry-autofill.js`

- **Где живёт.** Полноэкранный слой поверх реестра, `position: fixed`, отдельная разметка без `.drawer`.
- **Раскладка.** `grid-template-columns: 4fr 1fr`, это 80/20. Минимальная ширина формы 300 px: на узких окнах форма не сжимается, а счёт уменьшается.
- **Состояние** — в памяти модуля: `batch = [{ id, file, status, canvases, result, error }]`. Статусы: `queued → recognizing → ready → creating → created | error`.
- **Просмотр счёта.**
  - Слева показываются canvases из конвейера, для фото — `<img>`.
  - Кнопки «−», «+» и «По ширине», плюс Ctrl+колесо мыши. Масштаб — CSS `width`, прокрутка нативная.
- **Форма** — та же, что `fieldsHtml()` в `screen-registry.js` (вынести в общий помощник). Ниже неё:
  - подсветка полей по `flags`: класс `rg-flag` и подпись «проверьте по счёту» / «не найдено» / «QR: … · текст: …»;
  - пометка «как в прошлой заявке» у подставленных подразделения, категории и заявителя;
  - баннеры дубля и чужого покупателя над кнопками.
- **«Создать и дальше»:**
  1. `POST /requests` с полями и `recipientInn` / `invoiceNumber`;
  2. загрузка файла `kind=invoice`. Фото сжимаются тем же `Registry.prepareUpload`, а распознавание шло по несжатому оригиналу;
  3. если загрузка файла не удалась, заявка остаётся созданной, а у файла в полоске показывается «ошибка загрузки · Повторить». Это тот же приём, что в форме «Новая заявка»;
  4. затем открывается следующий файл в статусе `ready`. Если таких пока нет, а распознавание ещё идёт, показывается «Распознаём следующий счёт…».
- **«Убрать»** — файл удаляется из `batch`, освобождаются object URL и canvases.
- **Закрытие при несозданных файлах.** Срабатывают `confirm()` при закрытии экрана и `beforeunload` при закрытии вкладки.
- **Зона «Перетащите счета»** — новый блок над таблицей реестра в `screen-registry.js`, только на десктопе. В мобильной ветке `show()` его нет. Сюда же переезжает Ctrl+V: когда не открыта ни форма, ни карточка, вставка картинки идёт в автозаполнение.

### 6. Владение данными

Внешних таблиц не добавляется. Экспорт в Excel не меняется: 15 колонок плюс файлы, ИНН и № счёта не выгружаются. Старая таблица на Mail-диске заполняется вручную из экспорта, все колонки по-прежнему принадлежат программе.

### 7. Тесты

- **`backend/test/invoice-parse.test.js`** — разбор на текстовых фикстурах `backend/test/fixtures/invoices/*.txt`:
  - тексты трёх образцов, обезличенные: ФИО ИП, банковские счета, телефоны и e-mail заменены, ИНН ИП заменён на валидный по формату вымышленный;
  - строки QR в трёх кодировках (cp1251 подаётся заранее декодированной строкой: декодирование байтов — забота браузера).
- **`backend/test/registry-autofill-api.test.js`** — колонки, валидация ИНН, `lookup` со скрытыми значениями справочника и дублями.
- **Сквозной сценарий** `scripts/e2e/registry-autofill.e2e.js` на реальных файлах из каталога `E2E_INVOICES_DIR`, который лежит вне репозитория: пачка из трёх файлов → экран проверки → значения полей → «Создать и дальше» → заявки в реестре.

## Risks / Trade-offs

- [Кривое фото с телефона: OCR путает цифры] → QR подтверждает сумму и ИНН там, где он есть; без QR поле подсвечено «проверьте по счёту». Создание всегда только по кнопке после проверки. Облачный OCR вынесен за рамки и остаётся запасным путём.
- [Поставщик с нестандартной разметкой: правила не находят поля] → пустые поля подсвечены, и экран всё равно экономит время, потому что счёт открыт рядом. Новые шаблоны добавляются правилами в `invoice-parse.js` с фикстурой-тестом.
- [Репозиторий тяжелеет на 5–25 МБ из-за `vendor/`] → файлы меняются редко. При обновлении библиотек меняется ровно одна папка. Принято ради отказа от CDN.
- [Первый бросок медленный: загрузка библиотек и языка, прогрев воркера несколько секунд] → прогресс «Загружаем распознаватель…» в полоске. Дальше всё из кэша.
- [Подстановка по ИНН ошибается: тот же поставщик, но другое подразделение] → значение помечено «как в прошлой заявке» и правится вручную.
- [Дубль не пойман: у старых заявок нет ИНН] → предупреждение работает только для заявок, созданных после выкатки. Это принято.

## Migration Plan

1. Деплой обычный, `git pull && docker compose up -d --build`. Две колонки и индекс добавляет `db.migrate()`, старые заявки получают NULL.
2. Сервер ничего не скачивает и не устанавливает: `vendor/` отдаётся как статика.
3. **Откат** — вернуть предыдущий образ. Колонки остаются неиспользуемыми, ручная форма работает как раньше.
4. Архивация: только после `reestr-oplat`, см. proposal.md → Dependencies.
