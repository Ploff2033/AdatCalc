# Design

## Context

См. `proposal.md` и `specs/recipes/catalog-management/spec.md`. Сейчас `recipes` хранит завод, название и прайсовую цену, а `recipe_items` — состав. API отдаёт полный список рецептов; формы v2 используют его для нового заказа и исправления. Клиентские цены связаны с `recipe_id`. Интерфейс `/` использует те же API, поэтому фильтрация ответа сервера или изменение серверной проверки заказов затронули бы v1.

## Goals / Non-Goals

**Goals:**

- Хранить доступность каждого рецепта для новых заказов v2, сохраняя совместимость с текущими данными и клиентами API.
- Дать v2 создавать копию текущего рецепта как независимый черновик, который сохраняется с выключенной доступностью.
- Фильтровать доступные рецепты только в формах создания заказа v2 и показывать полный список при исправлении.

**Non-Goals:**

- Не менять поведение, ресурсы и исходники интерфейса `/`.
- Не вводить отдельные сущности марки, сезона или группы рецептов.
- Не копировать цены клиентов и не менять их хранение.

## Decisions

### Признак доступности на рецепте

Добавить `recipes.is_active BOOLEAN NOT NULL DEFAULT TRUE`; схема базы должна добавлять колонку через `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, поскольку `CREATE TABLE IF NOT EXISTS` не обновляет уже существующую таблицу. Так существующие строки и новые рецепты автоматически сохраняют текущее поведение. В ответе recipe API значение отдаётся как `isActive`. `POST` принимает необязательный `isActive` (по умолчанию `true`), `PUT` изменяет его только при явной передаче; старый клиент, не знающий поле, не включит и не выключит рецепт случайно.

Альтернатива — таблица сезонных версий или признак сезона. Она не нужна: сезон и марка задаются вручную в названии, а версии активируются независимо.

### Копирование через существующую форму и API

Кнопка копирования в v2 открывает несохранённую новую форму с названием, прайсовой ценой и составом исходного рецепта. Менеджер правит название/состав и сохраняет; v2 отправляет копию как новый рецепт с `isActive: false`. До сохранения в базе нет дубликата. Новая запись получает новый ID, поэтому `client_prices` исходного рецепта к ней не относятся и не клонируются.

Новый endpoint не добавляется: используется существующий POST, который уже проверяет завод и компоненты. Это сохраняет прежний путь валидации. Копирование доступно только в рамках завода текущего рецепта; изменение наименования и состава выполняется обычным редактированием формы.

### Фильтр только на стороне форм v2

Recipe API продолжает возвращать все рецепты и признак `isActive`. Экран справочника v2 показывает и активные, и выключенные, позволяя менять их состояние. Формы нового заказа на ПК и телефоне строят варианты из активных рецептов. В режиме исправления список не фильтруется, поэтому можно сохранить выключенный рецепт заказа или заменить его на любой другой.

Не фильтровать API глобально и не проверять доступность при общем `POST /api/orders`: оба изменения затронули бы v1, который в рамках change остаётся прежним и продолжает принимать выключенные рецепты.

### Права

Использовать действующую модель доступа: управление рецептурами и их доступностью — manager и admin; чтение для форм — по текущим правилам. Новые роли и права не вводятся.

## Risks / Trade-offs

- **Выключенный рецепт остаётся доступен через `/` и общий API создания заказа** → это намеренная совместимость до сворачивания v1; интерфейс v2 скрывает его только при создании нового заказа.
- **У уже открытой формы может остаться загруженный список до обновления данных** → при следующей загрузке справочника v2 применяет актуальные значения; realtime-синхронизация не добавляется.
- **Копия сезонной версии не наследует индивидуальные цены клиента** → это ожидаемо: новая рецептура имеет отдельный ID, цену клиента менеджер задаёт для неё отдельно.

## Migration Plan

1. Добавить колонку с `NOT NULL DEFAULT TRUE`; существующие рецепты становятся включёнными без переписывания связанных заказов и цен.
2. Развернуть совместимый API: старые POST/PUT без нового поля сохраняют включённое состояние новых рецептов и текущее состояние редактируемого рецепта.
3. Развернуть функции каталога и выбора рецептов в v2.
4. При откате приложения оставить колонку: старая версия её игнорирует. Не удалять колонку автоматически, чтобы не терять состояния, уже выставленные пользователями.
