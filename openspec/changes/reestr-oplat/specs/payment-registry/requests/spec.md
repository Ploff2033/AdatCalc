# Spec Delta

## Purpose

Реестр заявок на оплату. Admin заводит заявки с суммой и получателем, учредитель принимает по ним решение, admin отмечает фактические оплаты. Система считает остатки и итоги. Сам платёж проводится вне системы.

## ADDED Requirements

### Requirement: Создание заявки
Система SHALL позволять admin создать заявку на оплату. Обязательные поля:
- Подразделение (из справочника реестра);
- Категория (из справочника реестра);
- Получатель (текст);
- Сумма (> 0, в рублях, до копеек);
- Цель расхода (текст).

Необязательные поля: Заявитель (текст), Основание (текст), Срок оплаты (дата). Новая заявка получает статус «Ожидает решения».

#### Scenario: Успешное создание
- **WHEN** admin создаёт заявку: подразделение «Стройка», категория «Материалы», получатель «ООО "ПРОМХИМ"», сумма 63 800,00, цель «Фанера 18 мм»
- **THEN** заявка сохраняется со статусом «Ожидает решения», и «Не оплачено» = 63 800,00

#### Scenario: Не заполнено обязательное поле
- **WHEN** admin отправляет заявку без получателя, или без категории, или с суммой 0, или с отрицательной суммой
- **THEN** система отклоняет запрос с сообщением, какое поле не заполнено или некорректно, и заявка не создаётся

#### Scenario: Скрытое значение справочника
- **WHEN** admin пытается создать заявку со скрытой категорией или скрытым подразделением
- **THEN** система отклоняет запрос

### Requirement: Номер заявки
Система SHALL присваивать каждой новой заявке номер вида `DDMMYY-N`, где `DDMMYY` — дата создания заявки, а `N` — сквозной порядковый номер заявки за всё время. Номер не меняется при последующих правках заявки.

#### Scenario: Формат номера
- **WHEN** 12.10.2026 создаётся 57-я по счёту заявка
- **THEN** её номер `121026-57`

#### Scenario: Сквозная нумерация через смену даты
- **WHEN** 13.10.2026 создаётся следующая заявка
- **THEN** её номер `131026-58`

#### Scenario: Номер не зависит от удалений
- **WHEN** заявка `121026-57` удалена, после чего создаётся новая заявка
- **THEN** новая заявка получает N = 58, номер 57 повторно не выдаётся

### Requirement: Подсказки для заявителя и получателя
При вводе полей «Заявитель» и «Получатель» система SHALL предлагать ранее введённые в реестре значения этого поля. Значение при этом можно ввести и новое, произвольное. С сотрудниками (`employees`) и клиентами (`clients`) эти поля не связаны.

#### Scenario: Подсказка получателя
- **WHEN** в реестре уже есть заявка с получателем «ООО "ПРОМХИМ"», и admin вводит «ПРОМ» в поле получателя
- **THEN** система предлагает «ООО "ПРОМХИМ"»

### Requirement: Решение по заявке
Учредитель или admin SHALL иметь возможность принять по заявке решение: «Одобрить», «Отклонить» или «Отложить». При одобрении «К оплате» по умолчанию равна Сумме, её можно уменьшить до значения больше 0. Комментарий к решению необязателен. Система запоминает дату решения.

#### Scenario: Одобрение в одно нажатие
- **WHEN** учредитель нажимает «Одобрить» по заявке на 63 800,00, не меняя сумму
- **THEN** статус становится «Одобрена», «К оплате» = 63 800,00, сохраняется дата решения

#### Scenario: Одобрение части суммы
- **WHEN** учредитель одобряет заявку на 4 000 000,00 с «К оплате» = 1 500 000,00
- **THEN** статус «Одобрена», «К оплате» = 1 500 000,00, «Не оплачено» = 1 500 000,00

#### Scenario: «К оплате» вне допустимых границ
- **WHEN** при одобрении «К оплате» указана 0 или больше Суммы
- **THEN** система отклоняет решение

#### Scenario: Отклонение с причиной
- **WHEN** учредитель отклоняет заявку с комментарием «Есть на складе»
- **THEN** статус «Отклонена», комментарий сохранён, «Не оплачено» = 0

#### Scenario: Отложить без причины
- **WHEN** учредитель нажимает «Отложить» без комментария
- **THEN** статус «Отложена», и сама в «Ожидает решения» заявка не возвращается

### Requirement: Изменение решения
Учредитель или admin SHALL иметь возможность изменить решение, пока «Не оплачено» > 0 или заявка не одобрена. Новое значение «К оплате» не может быть меньше суммы уже внесённых оплат. Отклонить или отложить заявку, по которой уже есть оплаты, нельзя.

#### Scenario: Из «Отложена» в «Одобрена»
- **WHEN** учредитель одобряет ранее отложенную заявку
- **THEN** статус становится «Одобрена», дата решения обновляется

#### Scenario: Урезать «К оплате» ниже оплаченного
- **WHEN** по заявке оплачено 1 000 000,00, и учредитель меняет «К оплате» на 800 000,00
- **THEN** система отклоняет изменение

#### Scenario: Отклонить частично оплаченную
- **WHEN** по заявке уже есть оплата, и учредитель нажимает «Отклонить»
- **THEN** система отклоняет действие с сообщением, что сначала нужно удалить оплаты

### Requirement: Внесение оплат
Admin SHALL иметь возможность внести по заявке одну или несколько оплат: дата, сумма и, по желанию, файл платёжки. Оплата допускается только по заявке в статусе «Одобрена» или «Частично оплачена». Сумма оплаты > 0 и не больше «Не оплачено». Дата оплаты не позже сегодняшней.

#### Scenario: Первая частичная оплата
- **WHEN** по заявке с «К оплате» 1 500 000,00 admin вносит оплату 1 000 000,00 датой 12.10.2026
- **THEN** статус «Частично оплачена», «Оплачено» = 1 000 000,00, «Не оплачено» = 500 000,00

#### Scenario: Закрывающая оплата
- **WHEN** по той же заявке admin вносит ещё 500 000,00
- **THEN** статус «Оплачена», «Не оплачено» = 0, «Дата фактической оплаты» = дата последней оплаты

#### Scenario: Переплата
- **WHEN** «Не оплачено» = 500 000,00, и admin вносит 600 000,00
- **THEN** система отклоняет оплату с сообщением, что сначала нужно увеличить «К оплате»

#### Scenario: Оплата без одобрения
- **WHEN** admin вносит оплату по заявке в статусе «Ожидает решения», «Отложена» или «Отклонена»
- **THEN** система отклоняет оплату

#### Scenario: Дата из будущего
- **WHEN** 12.10.2026 admin вносит оплату датой 13.10.2026
- **THEN** система отклоняет оплату

### Requirement: Расчёт «Не оплачено» и статуса
Система SHALL вычислять «Оплачено» как сумму всех оплат заявки. «Не оплачено» вычисляется так:
- без решения или при «Отложена» — Сумма;
- при «Отклонена» — 0;
- при одобрении — «К оплате» − «Оплачено».

Статус одобренной заявки вычисляется по оплатам: «Одобрена» (оплат нет), «Частично оплачена» (0 < Оплачено < К оплате), «Оплачена» (Оплачено = К оплате).

#### Scenario: Без решения
- **WHEN** заявка на 63 800,00 ещё ждёт решения
- **THEN** «Не оплачено» = 63 800,00

#### Scenario: Отложенная
- **WHEN** заявка на 52 000,00 отложена
- **THEN** «Не оплачено» = 52 000,00

#### Scenario: Пересчёт после удаления оплаты
- **WHEN** у заявки с «К оплате» 84 000,00 две оплаты (50 000,00 и 34 000,00) и статус «Оплачена», и admin удаляет оплату 34 000,00
- **THEN** «Оплачено» = 50 000,00, «Не оплачено» = 34 000,00, статус «Частично оплачена»

#### Scenario: Увеличение «К оплате» у оплаченной
- **WHEN** у оплаченной заявки (К оплате 1 500 000,00 = Оплачено) учредитель поднимает «К оплате» до 2 000 000,00
- **THEN** статус «Частично оплачена», «Не оплачено» = 500 000,00

### Requirement: Правка и удаление
Admin SHALL иметь возможность в любой момент изменить любое поле заявки и удалить любую оплату. Решение при правке заявки не сбрасывается, история изменений не ведётся. Система запоминает дату последнего изменения полей заявки. Если заявку меняли после решения, карточка показывает это рядом с датой решения. Если после правки Сумма стала меньше «К оплате», «К оплате» уменьшается до Суммы.

#### Scenario: Правка после одобрения
- **WHEN** 13.10 admin меняет получателя у заявки, одобренной 12.10
- **THEN** статус и «К оплате» не меняются, в карточке видно «изменена 13.10 после решения 12.10»

#### Scenario: Уменьшение суммы ниже «К оплате»
- **WHEN** у одобренной заявки «К оплате» = 63 800,00, и admin меняет Сумму на 60 000,00
- **THEN** «К оплате» = 60 000,00

#### Scenario: Уменьшение суммы ниже оплаченного
- **WHEN** по заявке оплачено 50 000,00, и admin меняет Сумму на 40 000,00
- **THEN** система отклоняет правку

### Requirement: Удаление заявки
Admin SHALL иметь возможность удалить заявку, по которой нет оплат. Вместе с заявкой удаляются её файлы. Заявку с оплатами удалить нельзя.

#### Scenario: Удаление заявки без оплат
- **WHEN** admin удаляет заявку без оплат с двумя файлами
- **THEN** заявка и оба файла удаляются, ссылки на файлы перестают открываться

#### Scenario: Удаление заявки с оплатой
- **WHEN** admin удаляет заявку, по которой есть оплата
- **THEN** система отклоняет удаление с сообщением, что сначала нужно удалить оплаты

### Requirement: Порядок списка
Система SHALL показывать активные заявки группами в таком порядке:
1. «Ожидает решения»;
2. «Одобрена» и «Частично оплачена»;
3. «Отложена».

Внутри группы заявки сортируются по сроку оплаты: ближайший первым, без срока в конце. Заявки «Оплачена» и «Отклонена» показываются только в режиме «Закрытые». У каждой группы видны количество заявок и сумма «Не оплачено».

#### Scenario: Сортировка внутри группы
- **WHEN** ждут решения заявки со сроками 15.10, 10.10 и без срока
- **THEN** порядок: 10.10, 15.10, без срока

#### Scenario: Закрытые скрыты
- **WHEN** учредитель открывает реестр в режиме «Активные»
- **THEN** оплаченные и отклонённые заявки не показываются

### Requirement: Просроченные заявки
Система SHALL помечать заявку просроченной, если срок оплаты раньше сегодняшней даты, а «Не оплачено» > 0. Такая заявка выделяется красным в списке у admin и у учредителя.

#### Scenario: Просрочка
- **WHEN** сегодня 12.10.2026, а у заявки срок 10.10.2026 и «Не оплачено» 38 600,00
- **THEN** заявка выделена как просроченная

#### Scenario: Срок прошёл, но оплачено
- **WHEN** срок 10.10.2026 прошёл, а заявка «Оплачена»
- **THEN** заявка не выделяется

### Requirement: Фильтры
Система SHALL фильтровать список по статусу, подразделению, категории и периоду создания заявки. Итоги, суммы групп и экспорт учитывают выбранные фильтры.

#### Scenario: Фильтр по подразделению
- **WHEN** выбран фильтр подразделения «Теберда»
- **THEN** в списке и итогах учитываются только заявки «Теберды»

### Requirement: Итоги
Система SHALL показывать над списком итоги по заявкам, попавшим в фильтры:
- «Ожидает решения» — сумма и количество;
- «К оплате» — Σ «Не оплачено» по одобренным и частично оплаченным, плюс их количество;
- «Просрочено» — Σ «Не оплачено» по просроченным, плюс их количество;
- «Оплачено» — сумма оплат, датированных выбранным периодом.

#### Scenario: Расчёт итогов
- **WHEN** ждут решения заявки на 38 600,00 и 27 352,00; одобрена заявка на 186 000,00 без оплат; частично оплачена заявка с «К оплате» 84 000,00 и оплатой 50 000,00 от 04.10; период — октябрь 2026
- **THEN**
  - «Ожидает решения» = 65 952,00 (2 заявки);
  - «К оплате» = 186 000,00 + 34 000,00 = 220 000,00 (2 заявки);
  - «Оплачено» = 50 000,00

### Requirement: Реестр не затрагивает другие разделы
Создание, решение, оплата, правка и удаление в реестре SHALL NOT создавать, менять или удалять записи ДДС, остатки, заказы, справочники заводов, сотрудников и клиентов. Не меняются и категории ДДС.

#### Scenario: Оплата не попадает в ДДС
- **WHEN** admin вносит оплату 63 800,00 по заявке подразделения «Джага»
- **THEN** в ДДС завода «Джага» не появляется новых записей, синхронизация ДДС с Mail.ru не запускается

### Requirement: Доступ к реестру
Реестр (чтение и все действия) SHALL быть доступен только admin и учредителю по его ссылке. Учредитель только принимает решения: он не создаёт, не правит и не удаляет заявки и оплаты. Manager, анонимные работники по ссылке завода и общая ссылка работников доступа к реестру не имеют.

#### Scenario: Manager
- **WHEN** manager открывает реестр или вызывает его API
- **THEN** раздел не показывается, API отвечает отказом в доступе

#### Scenario: Работник по ссылке завода
- **WHEN** запрос к API реестра приходит с токеном ссылки завода
- **THEN** система отвечает отказом в доступе

#### Scenario: Учредитель пытается внести оплату
- **WHEN** учредитель по своей ссылке пытается внести оплату или изменить сумму заявки
- **THEN** система отвечает отказом в доступе
