# Design: Реестр оплат

## Context

Зачем это нужно, см. proposal.md («Why»); требования — в `specs/payment-registry/*` и `specs/backups`. Ниже то, что в текущем коде определяет подход:

- **Роли.** Вход по паролю даёт сессию с ролью `admin` или `manager` (`backend/handlers/auth.js`, `ROLE_RANK` в `backend/router.js`). Анонимный работник ходит с `?token=` ссылки завода или общей ссылки: `plants.resolveToken`, `config.checkUniversalToken`. Роль на маршруте проверяет `hasRole(role, route.role)`.
- **Файлы.** Фото чеков ДДС приходят data-URL внутри JSON (`backend/uploads.js`): только изображения, до 3 МБ. Лимит тела на маршрутах ДДС — 4 МБ. Раздача идёт без авторизации через `backend/static.js` (`/uploads/...`). Папка `uploads` примонтирована томом (`docker-compose.yml:33`). Имена файлов строятся из `db.genId` (время + 6 символов base36), то есть их можно угадать.
- **Telegram.** `backend/telegram.js`: один бот и один `telegram_chat_id` из `config`. `send()` выполняется с ретраями, уведомления вызываются без `await`.
- **Экспорт.** `frontend-v2/js/xlsx-writer.js` уже умеет гиперссылки (`opts.hyperlinks`), так сделан экспорт ДДС в `screen-cash.js::exportToExcel`.
- **Frontend v2.** Хэш-роутер (`router.js`, `MIN_ROLE`), десктоп и мобильная разметка переключаются по `Viewport.isMobile()` (≤ 860px). Ссылки работников выглядят как `/v2/?token=...`.
- **Схема БД.** Миграции идут через `backend/schema.sql` (`CREATE TABLE IF NOT EXISTS` / `ALTER ... ADD COLUMN IF NOT EXISTS`), их применяет `db.migrate()` при старте.
- **Тестов в проекте нет**: ни тестового раннера, ни зависимостей под него.

## Goals / Non-Goals

**Goals:**
- Реестр — самостоятельный модуль. Ни одна существующая таблица, кроме `config` (две новые колонки), не меняется.
- Учредитель — отдельный тип доступа по токену. Он не трогает существующие роли и не даёт доступа ни к чему, кроме API реестра.
- Вся логика статусов и сумм собрана в чистых функциях, их можно покрыть `node:test` без БД.

**Non-Goals:**
- Не переписываем общую модель ролей (`ROLE_RANK`) и сессии.
- Не переносим ДДС на новый механизм загрузки файлов.
- Не делаем realtime-обновление: учредитель видит изменения после обновления экрана.

## Decisions

### 1. Данные: пять новых таблиц, статус вычисляется

```
pay_categories   (id, name, hidden, created_at)            -- уникальность lower(name)
pay_units        (id, name, hidden, created_at)            -- «Подразделения реестра»
pay_requests     (id, seq SERIAL UNIQUE, number TEXT UNIQUE,
                  unit_id → pay_units, category_id → pay_categories,
                  applicant, basis, recipient, purpose, amount NUMERIC(14,2),
                  due_date DATE NULL,
                  decision TEXT NULL  -- null | approved | rejected | postponed
                  approved_amount NUMERIC(14,2) NULL, decision_comment, decided_at,
                  created_at, updated_at)
pay_payments     (id, request_id → pay_requests ON DELETE RESTRICT,
                  paid_on DATE, amount NUMERIC(14,2), created_at)
pay_files        (id, request_id → pay_requests ON DELETE CASCADE,
                  payment_id → pay_payments ON DELETE CASCADE NULL,
                  kind TEXT, original_name, mime, size_bytes, stored_name UNIQUE, created_at)
config + owner_token TEXT, + telegram_registry_chat_id TEXT
```

- **Статус не храним.** Его определяют `decision`, `approved_amount` и Σ оплат. Чистая функция `computeState(request, payments)` возвращает `{ status, paid, unpaid, overdue }`. Так же сделано в ДДС: «сторнирована» там вычисляется, а не хранится флагом (см. комментарий к `cash_entries`). Альтернатива — колонка `status`. Отвергнута: рассинхрон при удалении оплаты или правке «К оплате».
- **Номер.** `seq` берётся из sequence, поэтому номер не выдаётся повторно после удаления. `number = to_char(created_at, 'DDMMYY') || '-' || seq` вычисляется один раз при INSERT и хранится, чтобы правки его не меняли.
- **«Сегодня».** Для номера, проверки «дата оплаты не позже сегодня» и просрочки «сегодня» берётся по `Europe/Moscow`, а не по часовому поясу контейнера: `now() AT TIME ZONE 'Europe/Moscow'`. Иначе после 21:00 по Москве на UTC-сервере номер получит вчерашнюю дату. DATE-колонки уже приходят строкой (`types.setTypeParser(1082)` в `db.js`).
- **Деньги.** Тип `NUMERIC(14,2)`, на сервере суммы сравниваются в копейках (целые), чтобы избежать ошибок float. «Одобрить» без суммы значит `approved_amount = amount`.
- **Справочники.** Отдельные таблицы, а не JSON в `config`: на них ссылаются внешние ключи, и проверка «используется ли значение» сводится к одному `EXISTS`.
- **Сумма и «К оплате».** Если после правки Суммы она стала меньше `approved_amount`, сервер понижает `approved_amount` до Суммы в той же транзакции. Если Сумма меньше Σ оплат, правка отклоняется (409).

### 2. Доступ учредителя: токен в заголовке, псевдороль `owner`

- **Ссылка** вида `/v2/?owner=<token>#/registry/<number>`. Параметр отдельный, не `token`, чтобы `Plant.resolve()` и логика ссылок работников его не видели.
- **Фронт.** При старте `app.js` видит `?owner=`, проверяет его через `GET /api/registry/owner/check` и запускает урезанную оболочку: только экран реестра, без сайдбара, нижней навигации и выбора завода. Токен **остаётся в адресе страницы** и не прячется в `sessionStorage`. Так ярлык «На экран Домой» и повторное открытие из Telegram работают сами по себе, а встроенный браузер Telegram не теряет вход между открытиями.
- **API.** Каждый запрос учредителя несёт заголовок `X-Owner-Token`. Для маршрутов `/api/registry/*` в `router.js` добавляется резолвер: роль сессии `admin` → `admin`; иначе валидный `X-Owner-Token` (сравнение через `crypto.timingSafeEqual`) → `owner`; иначе `null`.
- **Права.** У маршрутов реестра свой список допустимых ролей: чтение и решение — `['admin', 'owner']`, всё остальное — `['admin']`. Проверка не идёт через `ROLE_RANK`, поэтому `owner` никак не вписывается в иерархию manager/admin. На остальных маршрутах заголовок не читается, и учредитель там — аноним.
- **Токен** генерируется тем же `genToken()`, что у заводов, и заполняется при миграции, если пуст (`db.js::backfillOwnerToken`, по образцу общего токена работников). Ссылка в Настройках есть сразу. Перевыпуск: `POST /api/registry/owner/reissue` (admin) перезаписывает значение.
- **Альтернатива** — выдавать по ссылке сессионную cookie с ролью `owner`. Отвергнута: встроенный браузер Telegram часто не хранит cookie между открытиями, а ссылка с токеном и так должна работать сама по себе (решение «вариант А»).

### 3. Файлы: отдельный upload, сырое тело, свой каталог

- **Загрузка.** `POST /api/registry/requests/:id/files?kind=invoice&name=<urlencoded>`: тело запроса — сами байты файла, `Content-Type` — его MIME. Не multipart и не data-URL: base64 раздул бы 10 МБ PDF до ~13,4 МБ JSON, а парсер multipart — лишний код без зависимостей.
- **Лимит.** `readBody`-аналог с лимитом 10 МБ. Сверх лимита — 413.
- **Тип файла** проверяется по сигнатуре (magic bytes), а не только по заголовку: `%PDF`, JPEG `FF D8 FF`, PNG `89 50 4E 47`, WEBP `RIFF....WEBP`. Прочее — 415.
- **Хранение.** `backend/uploads/registry/<stored_name>`, где `stored_name = crypto.randomBytes(16).toString('hex') + ext` (128 бит). Раздача идёт через существующий `/uploads/`, `Content-Disposition: inline`, для PDF — `Content-Type: application/pdf`, чтобы телефон открыл встроенный просмотрщик.
- **Новые заявки.** Файлы загружаются после создания записи заявки: форма сначала сохраняет заявку, потом по очереди шлёт файлы с прогрессом. Если файл не загрузился, заявка остаётся, а у файла показывается «Повторить».
- **Фото** сжимаются существующим `photo-compress.js`. Ctrl+V и drag-and-drop работают только на десктопной форме.
- **Удаление.** Сначала удаляется строка БД, затем файл на диске. Если `unlink` упал, остаётся «осиротевший» файл, ссылку на который уже никто не знает. Это допустимо.
- **Маршрут платёжки:** `POST /api/registry/payments/:id/file`, не больше одной на оплату. Новая заменяет старую.

### 4. API

Все маршруты под `/api/registry/`:

| Метод | Путь | Роли | Что делает |
|---|---|---|---|
| GET | `requests?status=&unit=&category=&from=&to=&closed=` | admin, owner | список с вычисленным состоянием, оплатами и файлами |
| GET | `requests/:id` | admin, owner | карточка |
| POST | `requests` | admin | создать (+ уведомление) |
| PUT | `requests/:id` | admin | правка полей |
| DELETE | `requests/:id` | admin | удалить (409, если есть оплаты) |
| POST | `requests/:id/decision` | admin, owner | `{decision, approvedAmount?, comment?}` (+ уведомление) |
| POST | `requests/:id/payments` | admin | `{paidOn, amount}` |
| DELETE | `payments/:id` | admin | удалить оплату и её файл |
| POST/DELETE | `requests/:id/files`, `files/:id`, `payments/:id/file` | admin | файлы |
| GET | `suggest?field=applicant\|recipient&q=` | admin | подсказки (DISTINCT, до 10) |
| GET/POST/PUT/DELETE | `categories`, `units` | GET: admin, owner; запись: admin | справочники |
| GET | `owner/check` | по заголовку | 200 или 401 |
| POST | `owner/reissue` | admin | новый токен |
| PUT | `settings` | admin | `telegramRegistryChatId` |
| POST | `telegram-test` | admin | тестовое сообщение в чат реестра |

- **Фильтр периода** для списка применяется к `created_at`. Для итога «Оплачено» тот же период применяется к `paid_on` оплат.
- **Итоги** считает сервер в ответе списка (`totals`), чтобы экран и экспорт брали одни и те же числа.
- **Ошибки валидации** возвращаются через существующий `HttpError` текстом на русском, по образцу остальных handler'ов.

### 5. Frontend

- **Десктоп для admin:** `screen-registry.js`, новый маршрут `registry` в `router.js` с `MIN_ROLE.registry = 'admin'`, пункт «Реестр оплат» в сайдбаре `shell.js`. Вёрстка по макету `Payments`/`PaymentsCard`/`PaymentsNew`: 4 плитки итогов, «Активные» / «Закрытые», фильтры, таблица по группам, боковая карточка, форма новой заявки. Карточка отличается от макета списком оплат («+ Оплата»: дата, сумма, платёжка; удаление строки), а не одним полем «Оплачено».
- **Телефон для учредителя:** `mobile-registry.js` по макету `MobileRegistry`/`MobilePhoto`: карточки по группам, кнопки решения, миниатюры, полноэкранное фото. Отдельная карточка заявки с полем «К оплате» и комментарием. Admin на телефоне видит тот же мобильный экран и в дополнение может внести оплату.
- **Настройки:** секция «Реестр оплат» в `screen-settings.js`, только для admin:
  - ссылка учредителя («Копировать», «Перевыпустить»);
  - ID чата реестра и «Отправить тестовое»;
  - два списка справочников (добавить, переименовать, скрыть или показать, удалить).
- **Экспорт** собирается на клиенте через `XlsxWriter.build` с `hyperlinks` из данных ответа списка. Абсолютные URL файлов: `location.origin + '/uploads/registry/' + stored_name`.

### 6. Telegram

В `telegram.js` добавляется `notifyRegistry(text)`: берёт тот же `telegram_bot_token`, но `telegram_registry_chat_id`. Если чат пуст — молча выходит. Вызывается без `await`, ошибки уходят в `console.error`, как у `notifyOrderCreated`. Ссылка в сообщении: `<публичный origin>/v2/?owner=<token>#/registry/<number>`.

Origin берётся из нового необязательного env `PUBLIC_BASE_URL`, а если его нет — из заголовков `Host`/`X-Forwarded-Proto` запроса, вызвавшего уведомление. Текст экранируется существующим `escapeHtml`.

### 7. Бэкап

`backup.sh` после дампа делает `tar -czf "$BACKUP_DIR/uploads-$STAMP.tar.gz" -C <каталог compose> uploads`. Путь задаётся `UPLOADS_DIR`, по умолчанию `$(dirname "$0")/../uploads`. Ротация `find ... -name 'uploads-*.tar.gz' -mtime +N -delete`. `restore.sh` получает необязательный второй аргумент — архив uploads. Если он не передан, скрипт ищет `uploads-<та же метка>.tar.gz` рядом с дампом, а если его нет, восстанавливает только базу, как раньше.

### 8. Владение данными

Внешней таблицы нет. Программа — единственный владелец всех полей. Excel — разовая выгрузка: правки в нём в программу не возвращаются.

### 9. Правка `openspec/config.yaml`

Строка «Этап оплаты (решение и платёж) вне системы: им занимается учредитель в Google-таблице» заменяется на: «Решение по оплате принимается в реестре оплат программы; сам платёж проводит бухгалтер вне системы, интеграции с банком нет».

## Risks / Trade-offs

- [Ссылку учредителя переслали или в чате реестра есть посторонние, и кто-то принял решение за учредителя] → Перевыпуск в Настройках сразу отключает старую ссылку. Чат реестра admin выбирает сам. Риск принят пользователем (вариант А).
- [Файлы со счетами открываются без входа] → Имена из 128 бит случайности, листинга каталога нет (`static.js` с `noFallback`). Принято ради открытия из Excel у бухгалтера.
- [Диск VPS заполнится сканами] → 10 МБ × 10 файлов — это потолок для заявки, а не норма. Размер `uploads` выводится в лог бэкапа (`du -h`).
- [Nginx или прокси перед приложением режет тела больше 1 МБ, и PDF не грузится] → При выкатке проверить `client_max_body_size` (см. Migration Plan). Ошибку 413 показать понятным текстом.
- [Общий пароль admin: не видно, кто — вы или бухгалтер — внёс оплату] → Принято в интервью.
- [Нет истории: учредитель одобрил одну сумму, а её потом поменяли] → Карточка показывает «изменена после решения». Полная история — второй тур.
- [Одновременные решения admin и учредителя по одной заявке] → Побеждает последнее (`UPDATE` в транзакции, состояние пересчитывается). Для MVP допустимо.

## Migration Plan

1. Деплой обычный: `git pull && docker compose up -d --build`. Таблицы и колонки создаёт `db.migrate()`, существующие данные не меняются.
2. Проверить лимит тела у прокси перед приложением, при необходимости поднять до 12 МБ.
3. Обновить `backup.sh` и `restore.sh` на сервере (они в репозитории), прогнать бэкап вручную и убедиться, что архив `uploads-*.tar.gz` появился.
4. В Настройках завести категории и подразделения, задать ID чата реестра, нажать «Отправить тестовое», скопировать ссылку учредителю.
5. **Откат.** Вернуть предыдущий образ. Новые таблицы и колонки останутся в базе неиспользуемыми и ничему не мешают. Каталог `uploads/registry` можно оставить.
