# Координатор задач

## Вход и выбор маршрута

Работай из корня Calc. Прочитай `openspec/config.yaml`, относящиеся к задаче
основные спеки и код. Проверь существующие незавершённые задачи и изменения
пользователя. Если Git недоступен, сообщи об ограничении; не выдавай состояние
рабочего дерева за чистое. Выбирай существующую задачу по контексту; при нескольких
подходящих уточни выбор. Не создавай дубль.

Коротко сообщи выбранный маршрут и причину:

| Маршрут | Условие | Порядок |
|---|---|---|
| bugfix | Код нарушает однозначную действующую спеку | Воспроизведение → исправление → регрессионная проверка → приёмка |
| small-change | Ограниченное изменение поведения с понятными зависимостями | Короткое интервью → компактный полный пакет change → согласование → реализация → проверка |
| feature | Новая возможность или существенные изменения прав, данных, расчётов | Интервью → полный пакет change → согласование → реализация → проверка |
| discovery | Для запроса на реализацию пока неясны цель или осуществимость | Исследование → решения пользователя → выбор следующего маршрута |

Размер diff не определяет риск. Если ожидаемое поведение бага не закреплено
или противоречиво, сначала выясни его и переведи задачу в small-change/feature.
Прототип создавай только после определения его цели и разрешения пользователя;
результат прототипа не считай готовой реализацией.
Изменения только документации, инструкций и конфигурации процесса выполняй
пропорционально задаче: согласованный текст из разговора уже является основанием
для реализации; не создавай рекурсивный change ради настройки самого процесса.

## Интервью и подготовка

Для интервью прочитай [grilling от Matt Pocock](../grilling/SKILL.md).
[grill-me](../grill-me/SKILL.md) — альтернативная точка входа в тот же навык;
если инструмент Skill недоступен, прочитай grilling и следуй ему напрямую.
Используй авторский порядок: независимые вопросы одним раундом, зависимые —
после ответов на предыдущий раунд. Каждый вопрос сопровождай рекомендуемым
ответом и причиной. По просьбе пользователя переключайся на один вопрос за раз.
Факты из кода, спецификаций и инструментов выясняй сам. Спрашивай
пользователя о решениях, не о доступных тебе фактах. Не проводи формальное
интервью, если нужные решения уже приняты в переписке.

По применимости закрой цель, получателей результата, источники данных, роли,
права, границы ответственности, зависимости, ошибки и края сценариев, формулы
с примерами и ограничения совместимости. Противоречия показывай сразу.
Подтверждение общего понимания в grilling завершает интервью; затем готовь
пакет OpenSpec. Оно не заменяет согласование готового пакета перед кодом.
Не выдумывай ответы ради завершения этапа.

### Learnings: проверка завершения интервью

Перед переходом в planning отдельно перечисли принятые решения пользователя,
предположения агента и открытые вопросы. Пока остаются существенные вопросы
о поведении, данных или границах задачи, сохраняй этап interview и продолжай
опрос раундами; не создавай change или его пакет и не объявляй требования
согласованными. Несущественные технические решения принимай самостоятельно.

Короткое «да» относится только к конкретному вопросу или явно представленному
списку решений. Оно не закрывает остальные вопросы и не превращает
предположения агента в решения пользователя. Например, «да, вся сумма»
подтверждает сумму прихода, но не дату операции или возврат при отмене заказа.

После закрытия существенных вопросов покажи итоговое описание поведения,
включая края сценариев и границы задачи, и получи подтверждение общего
понимания. Только затем переходи к пакету OpenSpec; это подтверждение
не заменяет согласование готового пакета перед кодом. Не повторяй вопросы,
на которые пользователь уже явно ответил; его явные указания о процессе
имеют приоритет.

Для финансовых изменений обязательно проверь момент и дату операции, сумму,
исправления, отмены, смену способа оплаты, исторические данные и защиту от
дублей. По каждому пункту зафиксируй принятое правило, открытый вопрос либо
причину неприменимости. Не приравнивай правку документа к движению денег:
например, смена НДС сама по себе ещё не доказывает возврат наличных.

Для планирования/реализации/обновления/архивирования читай только соответствующий
доступный навык `.claude/skills/openspec-{propose,apply-change,update-change,archive-change}/SKILL.md`.
Для синхронизации доступен `.claude/skills/openspec-sync-specs/SKILL.md`.
Следуй фактической схеме, путям и шаблонам установленного CLI, а не предположению
о версии. При наличии CLI сначала получи `openspec list --json`, затем status
и instructions для выбранного change/артефакта; уточняй синтаксис через help.
Не инициализируй новый OpenSpec поверх существующего проекта.

Если локальных навыков нет, используй CLI и этот договор. Если CLI отсутствует,
сообщи об этом: можно исследовать, проводить интервью и готовить черновики в
записи задачи. Не имитируй успешную валидацию или архивирование; создание и
изменение официальных артефактов вручную требует явного выбора пользователя.

В текущей spec-driven схеме пакет включает proposal, delta-specs, design и tasks.
Для небольшого изменения сокращай содержание, а не обязательные артефакты.
Сценарии должны позволять проверить результат. Порядок и формат определяются
схемой и config. Основные спеки до приёмки не подменяй желаемым поведением.

Покажи готовый пакет и короткое резюме: поведение с примерами, границы,
существенные решения и критерии приёмки. Получи одно согласование перед кодом
для small-change/feature. Не запрашивай отдельное согласие на каждый документ.
Сохраняй уже данное разрешение; если пользователь заранее явно разрешил полный
цикл, следуй его указанию. Не выводи разрешение из молчания или ожидания.

## Реализация и изменение требований

После согласования продолжай самостоятельно: реализация → проверки → отчёт.
Технические решения в согласованных границах принимай сам. Отмечай задачи
выполненными только после реализации и предусмотренных проверок.

При новых требованиях оцени влияние на поведение, объём и зависимости.
Сначала покажи значимые отличия и согласуй их, затем обнови затронутые
артефакты согласованно и продолжи. Технические уточнения без изменения
согласованного поведения не требуют повторного согласования. Не сокращай
требования ради прохождения тестов. Независимое расширение предложи выделить
в отдельный change. Не начинай вторую задачу без запроса пользователя.

Не создавай дополнительные ветки, коммиты, PR или деплой только потому, что
задача достигла очередного этапа; выполняй их в рамках разрешения пользователя.

## Проверка, приёмка, завершение

Сопоставь выполненное со сценариями спеки. Выполни подходящие проверки согласно
config и влиянию изменения. Для исправления бага проверь исходное воспроизведение.
Для обратимых малозначимых правок документации достаточно проверки содержимого.
Отдельно укажи passed/failed/skipped и что не запускалось. Пропуск DB-тестов
из-за отсутствия базы не доказывает работоспособность сценариев с БД.

Покажи результат, проверки, ограничения и короткий сценарий ручной приёмки.
Если технические проверки блокированы, сохрани этап verification и блокер;
не объявляй задачу готовой. После успешных проверок — acceptance, а не done.
Исправляй несоответствия согласованной спеке без нового согласования объёма.

После подтверждения проверки на реальных данных выполни синхронизацию и
архивирование через доступный OpenSpec workflow, учитывая зависимости change.
Такое подтверждение в рамках этого процесса разрешает штатное завершение;
не спрашивай повторно о том же. Ошибки синхронизации и незавершённые задачи
устрани или явно согласуй исключения; не скрывай их статусом done.

## Сохранение и возобновление

До создания change сохраняй состояние в `docs/tasks/<task-id>.md` с уникальным
kebab-case идентификатором; создавай запись при начале работы, не для простого
обсуждения. После создания перенеси её в `<changeRoot>/workflow.md`, оставив
в исходной записи только ссылку. Для bugfix без change запись остаётся в docs/tasks.
Это дополнительная запись координатора, не новый обязательный артефакт схемы.
Для существующего change без записи восстанови её из файлов и разговора;
если разрешение на реализацию не установлено, не выдумывай его.

Сохраняй компактно:

- Маршрут и причина; ссылки на change, применимые требования и зависимости.
- Этап: discovery / interview / planning / approval / implementation /
  verification / acceptance / done. Блокер — отдельное поле, не потеря этапа.
- Цель, границы, решения, открытые вопросы.
- Согласование: дата, точный смысл ответа пользователя, согласованное поведение
  и версия пакета (снимок существенных решений или доступный идентификатор).
  При существенной правке явно помечай, какие изменения ещё не согласованы.
- Проверки: команды/сценарии, результаты и пропуски; подтверждение приёмки.
- Следующий шаг и что требуется от пользователя, если требуется.

Обновляй запись после существенного ответа, смены этапа, появления блокера и
перед завершением ответа с незаконченной работой. Не дублируй tasks и требования:
ссылайся на них. Не сохраняй секреты и персональные данные.
При возобновлении сверяй запись с реальными файлами, статусом CLI и результатами
проверок; устаревшая отметка не подтверждает выполнение. После архива обнови
ссылку из docs/tasks на архивную запись и только тогда отметь done. Bugfix без
change завершается в своей записи после проверок и приёмки, без архивирования.
